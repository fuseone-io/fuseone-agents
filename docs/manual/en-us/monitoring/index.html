Monitoring event dispatch

What can delay an event

Section titled “What can delay an event”

When a run finishes and its agent publishes an event, the worker’s event dispatcher opens the runs of the agents that listen for it. The dispatcher sweeps every fifteen seconds and reads finished runs forward from one cursor for the whole installation.

It reads only runs that finished before the oldest transaction still open in the database began. That is what guarantees no run is ever skipped: a transaction that is still open could commit a finished run with an earlier position, and the cursor must not have passed it. The price is that a long transaction anywhere in the database — a report, a manual psql session left open, a stuck migration — delays every event dispatch while it is open. Dispatch is delayed, never skipped: when the transaction ends, the waiting runs are dispatched on the next sweep.

On the Runtime health page

Section titled “On the Runtime health page”

Readers with access to the whole installation see an Event dispatch panel:

FieldMeaning
Waiting for the next sweepFinished runs past the cursor the dispatcher can read now. Normally zero or a handful, cleared within fifteen seconds.
Held by an open transactionFinished runs that committed after the oldest open transaction began. Sweeping more often does not reach them; ending that transaction does.
The oldest waiting run finished … agoThe lag: how long the earliest-finished run past the cursor has waited. When a count reached 1,000 it reads “at least”: only a sample was read.
Open transaction ageHow long the oldest open transaction has been open, shown when runs are held.
Healthy / DegradedDegraded once the lag passes five minutes, or once a count reaches 1,000 (the lag is then read from a sample and is only a lower bound, so it is never read as healthy).

A degraded dispatcher also appears under Needs attention. Degraded is not a failure: nothing is lost, and the platform keeps working.

Readers scoped to one company or area do not see this panel. The cursor belongs to the installation and its count covers every scope’s runs.

Prometheus metrics

Section titled “Prometheus metrics”

The worker’s metrics endpoint (--metrics-addr) exposes these, read on the worker’s first sweep and then once a minute:

MetricTypeMeaning
fuseone_event_dispatch_backlog_runs{state="ready"}gaugeRuns waiting for the next sweep.
fuseone_event_dispatch_backlog_runs{state="held_by_xmin"}gaugeRuns held by the oldest open transaction.
fuseone_event_dispatch_backlog_capped{state="ready"|"held_by_xmin"}gauge1 when that state’s count stopped at 1,000: it is at least that.
fuseone_event_dispatch_lag_secondsgaugeHow long the earliest-finished waiting run has waited. A lower bound when a count is capped.
fuseone_event_dispatch_held_by_xmingauge1 while committed runs wait on an open transaction.
fuseone_event_dispatch_oldest_xact_age_secondsgaugeAge of the oldest open transaction holding an id. Omitted when unknown.
fuseone_event_dispatch_oldest_xact_age_knowngauge0 when a transaction is open and its start cannot be seen.
fuseone_event_dispatch_degradedgauge1 once the lag passes five minutes, or whenever either count is capped.
fuseone_event_dispatch_observed_timestamp_secondsgaugeWhen the worker last read the backlog.
fuseone_event_dispatch_observe_failures_totalcounterBacklog reads that failed.

The only label is state, with two values. No run, agent or transaction id ever becomes a label. The gauges appear only after the first successful read, so a worker that never looked cannot report that dispatch is caught up.

The counts stop at 1,000 (shown as 1000+ on the page). The reading happens during the very incidents it describes, on every worker, so it is bounded: two index ranges of at most 1,001 rows each, however large the backlog grows. The lag is the earliest finish among the rows those ranges read — by the clock that stamped each finish, not by the order the feed reads them in. When a count is capped that is a sample, so the lag is a lower bound and the status is degraded.

The holder’s age, and why it is usually unknown

Section titled “The holder’s age, and why it is usually unknown”

The age of the open transaction comes from pg_stat_activity. PostgreSQL shows every role that another session holds a transaction, but shows when it began only to a superuser, a member of the session’s role, or a member of pg_read_all_stats. A plain application role sees the transaction is open and not its age: the panel says so, and fuseone_event_dispatch_oldest_xact_age_known reads 0.

That is the recommended state. pg_read_all_stats is not scoped to the platform’s database: it is a cluster-wide grant that lets the role read the statistics, the current queries and the client addresses of every session in every database on the server. On a cluster shared with other applications, granting it to the platform’s role would let anything that compromises the platform read other systems’ queries. The platform does not need it — the backlog counts, the lag and the health signal work without it — so keep the age unknown.

If you want the age without the broad grant, give the platform a narrow interface instead: a function owned by a privileged role that returns only the oldest transaction’s start, and nothing else.

The platform itself does not call such a function today. Point your own monitoring (a Prometheus SQL exporter, for example) at it, running as a dedicated monitoring role rather than as the platform’s.

When dispatch is held, a database administrator can always find the holder with their own role, as below.

When dispatch is held

Section titled “When dispatch is held”

  1. Check fuseone_event_dispatch_held_by_xmin. At 0 with a growing lag, the dispatcher itself is not sweeping: look at the worker logs for event dispatch failed.

  2. At 1, find the oldest open transaction:

    It can be in any database of the same PostgreSQL cluster.

  3. Ending that transaction releases dispatch. The held runs are dispatched on the next sweep, each once.
