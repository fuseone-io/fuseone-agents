Software factory

Software factory

Section titled “Software factory”

A software factory is a set of agents, each in one role, that take a repository’s issues from triage to a pull request ready to merge, driven by a GitHub Project board. The platform runs it with nothing but configuration: the roles are ordinary agents, the official GitHub MCP server is their only tool server, and the Gate governs every call they make.

This page is the operator’s path. The reasoning behind it is design note NT-013, and the role instructions live, reviewed like code, in factory/.

What the first version is

Section titled “What the first version is”
  • Three roles. Triage turns a new issue into a prepared card; the Reviewer reviews a pull request; QA checks it against CI and the acceptance criteria. Each role is an agent created in the console or the Studio.
  • One GitHub App per role. Each role reaches GitHub only through its own registration of the GitHub server, authenticated as its own App. The App’s permissions are the first limit, and its name is what signs the role’s comments and reviews.
  • Every role at copilot, with standing approvals forbidden. Every GitHub write a role proposes — a comment, a label, a review, a card move — waits for a person. The card claim below is the one write that does not. See Draft, copilot and autonomous.
  • A person merges. No role merges.
  • The board drives the work, with five lanes: Triagem, Preparado, Doing, Travado and Done. Inside Doing, labels mark where a pull request is: factory:needs-review, factory:changes-requested, factory:needs-qa and factory:ready-to-merge. Only a person takes a card out of Travado.
  • One card per run. A role wakes on its schedule, chooses a card, claims it with $fuseone.work_item.claim and works only that card. The claim is recorded in the run’s trail, and no other run of the same role can take a card that is held. Before the claim, Triage is told to list its lane only with projects_list, method list_project_items, so it sees the cards’ titles, which the board listing always returns. The same Projects tools can also return the board’s status updates, free text, and nothing in the platform stops a model from asking for them, because the Gate classifies a tool, not its method. The pilot accepts this within the claim’s limits below; preventing it needs the narrow tool that is deferred. A title is untrusted text: the role is told to use it only to tell cards apart and to choose by age and label, and it reads the issue’s body and comments after the claim. A title can still sway which card the model picks, and the claim needs no approval, even after untrusted text: it is a coordination operation, so two runs never wait on a person to reserve a card. A claim on the wrong card only holds that card for this role while the run is open, releases it when the run ends, and puts the run’s cost on that card. It writes nothing to GitHub, and every GitHub write after it waits for a person. A tool that picks and claims a card in one step, hiding even the title, is deferred.

The repository is public, so issue and pull request text is untrusted: a run that read it can never take a destructive action, and its GitHub writes need a person.

1. Create the GitHub Apps

Section titled “1. Create the GitHub Apps”

Create one GitHub App per role, install it only on the repository the factory works, and give it only what its tools need:

RoleRepository permissionsOrganisation permissions
TriageIssues: write, Pull requests: read, Metadata: readProjects: write
ReviewerPull requests: write, Issues: write, Contents: read, Checks: read, Commit statuses: read, Metadata: readProjects: write
QAPull requests: write, Issues: write, Contents: read, Checks: read, Commit statuses: read, Metadata: readProjects: write

QA’s verdict is a pull request review, so QA needs Pull requests: write just like the Reviewer. Generate a private key for each App and note its App id and installation id.

2. Register the GitHub server once per role

Section titled “2. Register the GitHub server once per role”

In the administration, register the hosted GitHub MCP server (https://api.githubcopilot.com/mcp/) three times, one per role, with the id github-<role>: github-triage, github-reviewer, github-qa. Choose the GitHub App credential and fill in that role’s App (see MCPs and credentials, section “GitHub App”).

The hosted server’s default toolsets do not include projects, so set the Toolsets field (sent as X-MCP-Toolsets) on every registration:

RoleToolsets
Triageissues,projects
Reviewerpull_requests,repos,issues,projects
QApull_requests,repos,issues,projects

The hosted server silently ignores a toolset name it does not know, so a typo shows up later, as a publish refused for missing tools.

3. Classify the tools

Section titled “3. Classify the tools”

Once each server is answering, classify every tool the roles declare (see What the platform stops before it happens).

Every read tool is untrusted — not only the ones that read an issue’s body. A listing returns text people wrote: projects_list returns the titles of the board’s issues and pull requests even when asked for no fields (#220).

Classify asTools
read, untrustedprojects_list, projects_get, search_pull_requests, search_issues, list_issues, issue_read, pull_request_read, get_file_contents, search_code, get_commit
writeadd_issue_comment, issue_write, pull_request_review_write, projects_write

Classify each tool on every role’s server: github-triage.projects_list and github-reviewer.projects_list are separate entries.

projects_write moves cards and can also remove an item. Classify it as a write, not destructive: a removed card can be added back, and a person approves every GitHub write. Classified destructive, it would be blocked outright, and every role that reads issue text and moves cards would be refused at publish.

4. Create the factory’s area

Section titled “4. Create the factory’s area”

Create an area for the factory, so its cost, budget and grants stay apart from every other agent, and give it a budget (see Costs and limits and Companies, areas and roles). The references use the area id factory.

Each reference also carries a per-run ceiling, so a looping role parks instead of spending:

RoleScheduleCeiling per runTool callsSteps
Triageevery hour at :00500,000 micros3060
Reviewerevery hour at :152,000,000 micros80160

Micros are millionths of the installation’s configured currency. Treat these values as a first calibration.

5. Create the roles

Section titled “5. Create the roles”

For each role, create the agent in the Studio from its reference: the frontmatter’s fields, and the body as its instructions.

  • Triage
  • Reviewer
  • QA

Then publish it — a new agent is a paused draft — set its stage to copilot and start it. The stage is not in the file, so it is always set in the console.

The console refuses to publish a tool the registered server does not offer, so a wrong tool name, or a missing toolset, is found here rather than at run time.

What the roles follow is in the same directory: RULEBOOK (the rules every role follows), REVIEW (the review format) and LANES (what done means for each lane and label). The role references README explains every line of a reference.

Changing a role

Section titled “Changing a role”

A change to a role is made in the reference first, reviewed by pull request, and then copied into the console. When the console and the reference disagree, the console has drifted.

After changing a registration’s toolsets, check that the server shows as reachable before trusting a publish. Its next discovery replaces its tools: a tool the new toolsets no longer offer leaves the catalogue, and the publish check refuses a role that still names it. A server that cannot be reached keeps the tools of its last successful discovery, so until it is reached again the catalogue still shows the old set.
