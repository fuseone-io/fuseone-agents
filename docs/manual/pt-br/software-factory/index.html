Fábrica de software

Fábrica de software

Section titled “Fábrica de software”

Uma fábrica de software é um conjunto de agentes, cada um num papel, que levam as issues de um repositório da triagem até um pull request pronto para merge, guiados por um board do GitHub Projects. A plataforma roda isso só com configuração: os papéis são agentes comuns, as ferramentas deles vêm do servidor MCP oficial do GitHub e do servidor MCP da própria fábrica, que move os cards do board e registra o veredito do QA, e o Gate governa cada chamada que fazem.

Esta página é o caminho de quem opera. O raciocínio por trás está na nota de desenho NT-013, e as instruções dos papéis ficam, revisadas como código, em factory/.

O que é a primeira versão

Section titled “O que é a primeira versão”
  • Seis papéis. A Triagem transforma uma issue nova num card preparado, ou passa o card para o Arquiteto com factory:needs-design quando ele precisa de um plano; o Arquiteto confere a mudança no código e escreve o plano e os critérios de aceite na issue; o Desenvolvedor faz uma mudança pequena e abre o pull request dela; o Revisor revisa um pull request; o QA confere o pull request contra o CI e os critérios de aceite; o Merger propõe o merge de um pull request pronto para isso, ou o devolve. Cada papel é um agente criado no console ou no Studio.
  • Um GitHub App por papel. Cada papel só alcança o GitHub pelos seus próprios registros, o do servidor do GitHub e o do servidor da fábrica, os dois autenticados como o seu próprio App. As permissões do App são o primeiro limite, e o nome dele é o que assina os comentários e revisões do papel e o status factory/qa do QA.
  • Ferramentas de board estreitas. Os cards andam com o move_card do servidor da fábrica, só pelas transições do próprio papel (a Triagem e o Arquiteto de Triagem para Preparado ou Travado; o Desenvolvedor, o Revisor e o QA de Doing para Travado, assim como o Merger; o Merger só chega a Done pelo close_merged, para uma PR mergeada), e nada sai de Travado. A Triagem e o Arquiteto preenchem Work type e Size com o set_card_fields, só em Triagem. Nenhum papel tem o projects_write do servidor do GitHub.
  • Todos os papéis em copiloto, com aprovações permanentes proibidas. Toda escrita no GitHub que um papel propõe — comentário, rótulo, revisão, card movido — espera uma pessoa. O claim do card, descrito abaixo, e o vínculo que o Desenvolvedor faz do pull request que acabou de abrir são as escritas que não esperam, e nenhuma das duas escreve no GitHub. Veja Rascunho, copiloto e autônomo.
  • O Merger propõe, uma pessoa aprova. O merge_if_ready do Merger relê o GitHub depois que uma pessoa aprova e só faz o merge quando a aprovação do Revisor, o factory/qa do QA e todos os checks esperados estão no head. O Merger não lê nada que alguém escreveu, então um texto de issue nunca consegue conduzir o run dele. Uma pessoa continua podendo fazer o merge à mão.
  • O board guia o trabalho, com cinco colunas: Triagem, Preparado, Doing, Travado e Done. Dentro de Doing, rótulos marcam em que ponto o pull request está: factory:needs-review, factory:changes-requested, factory:needs-qa e factory:ready-to-merge. Um card que o Desenvolvedor não consegue fazer sem um build recebe factory:needs-runtime na issue. Só uma pessoa tira um card de Travado.
  • Um card por run. Um papel acorda no seu horário, escolhe um card, faz o claim dele com $fuseone.work_item.claim e trabalha só nesse card. O claim fica registrado na trilha do run, e nenhum outro run do mesmo papel pode pegar um card que já está reservado. Antes do claim, a Triagem é instruída a listar a coluna só com o projects_list, método list_project_items, e assim vê os títulos dos cards, que a listagem do board sempre traz. As mesmas ferramentas de Projects também podem devolver os status updates do board, que são texto livre, e nada na plataforma impede o modelo de pedir esses dados, porque o Gate classifica a ferramenta, não o método. O piloto aceita isso dentro dos limites do claim descritos abaixo; impedir de fato exige a ferramenta específica que ficou para depois. Um título é texto não confiável: o papel é instruído a usar o título só para diferenciar os cards e a escolher por idade e rótulo, e lê o corpo e os comentários da issue depois do claim. Mesmo assim, um título pode influenciar qual card o modelo escolhe, e o claim não precisa de aprovação, nem depois de texto não confiável: é uma operação de coordenação, para que dois runs nunca esperem uma pessoa para reservar um card. Um claim no card errado só reserva esse card para o papel enquanto o run está aberto, libera o card quando o run termina e lança o custo do run nesse card. Ele não escreve nada no GitHub, e toda escrita no GitHub depois dele espera uma pessoa. Uma ferramenta que escolhe e faz o claim do card de uma vez, escondendo até o título, ficou para depois. O Arquiteto lista a coluna Triagem, e o Desenvolvedor a coluna Doing, do mesmo jeito, e os dois recebem a mesma instrução.
  • O histórico de um card. A linha Item do claim, na trilha de um run, leva a todos os runs que fizeram o claim do card, com as aprovações e o custo de cada papel (veja Ler uma execução). A issue e os pull requests vinculados a ela aparecem juntos: logo depois de abrir um pull request, o Desenvolvedor o vincula à issue do seu claim com $fuseone.work_item.link, e a partir daí os runs do Revisor e do QA nesse pull request entram no histórico da issue, marcados como Pull request. Abrir o histórico de um pull request vinculado mostra o histórico da issue e avisa isso. O vínculo não espera ninguém quando o próprio create_pull_request do run citou aquele pull request — respondido pelo servidor hospedado do GitHub registrado com o GitHub App do papel — e espera uma pessoa nos outros casos. Mantenha o resultado do create_pull_request como untrusted, o padrão: o vínculo é provado pelo pull request que a plataforma lê da resposta, não pela resposta, que continua marcando o run como não confiável, e toda escrita seguinte continua esperando uma pessoa; um pull request pertence a um só card para sempre, e um vínculo que você não pode ler aparece para você como se não existisse.

O repositório é público, então o texto de issues e pull requests não é confiável: um run que leu esse texto nunca pode executar uma ação destrutiva, e as escritas dele no GitHub precisam de uma pessoa.

1. Crie os rótulos

Section titled “1. Crie os rótulos”

O board encaminha pull requests e issues por rótulos, e o GitHub só aplica rótulos que o repositório já tem. Um papel que tenta pôr um rótulo que nunca foi criado falha nessa escrita, e o card fica onde estava, para ser escolhido de novo no próximo run. Crie todos os rótulos da fábrica uma vez, a partir de um clone do repositório em que a fábrica trabalha (ou acrescente --repo <dono>/<nome>). 2. Crie os GitHub Apps

Section titled “2. Crie os GitHub Apps”

Crie um GitHub App por papel, instale cada um só no repositório em que a fábrica trabalha e dê a ele só o que as ferramentas do papel precisam:

PapelPermissões no repositórioPermissões na organização
TriagemIssues: write, Pull requests: read, Metadata: readProjects: write
ArquitetoContents: read, Issues: write, Metadata: readProjects: write
RevisorPull requests: write, Issues: write, Contents: read, Checks: read, Commit statuses: read, Metadata: readProjects: write
QAPull requests: read, Issues: write, Contents: read, Checks: read, Commit statuses: write, Metadata: readProjects: write
DesenvolvedorContents: write, Pull requests: write, Issues: write, Metadata: readProjects: write
MergerContents: write, Pull requests: write, Checks: read, Commit statuses: read, Metadata: readProjects: write

O App do Merger faz o merge e escreve os comentários de texto fixo e os rótulos dele no pull request com Pull requests: write; ele não tem permissão de Issues (o canário do passo 3 comprova que isso basta). O veredito do QA é o status de commit factory/qa no head que ele conferiu, então o App dele precisa de Commit statuses: write. Ele não envia revisão, então só precisa de Pull requests: read: comenta o veredito e troca os rótulos do pull request pela API de Issues, que o Issues: write cobre (o canário do passo 3 comprova isso). O Arquiteto lê o código e só escreve em issues e no board: dê ao App dele Contents: read, nunca write, para que o GitHub recuse qualquer arquivo ou branch que tentem convencê-lo a escrever. Não dê a permissão Workflows ao App do Desenvolvedor: sem ela, o GitHub recusa qualquer mudança que o Desenvolvedor faça em .github/workflows. Gere uma chave privada para cada App e anote o ID do App e o ID da instalação.

Contents: write alcança todos os branches, inclusive o main. O Desenvolvedor é instruído a escrever só nos branches que ele mesmo cria em factory/, e a pessoa que aprova cada escrita vê o branch que ela indica, mas nenhum dos dois impede uma escrita. Por isso um ruleset é pré-requisito, não recomendação:

Antes de iniciar o Desenvolvedor, o main precisa ter o ruleset mínimo: pull request obrigatório antes do merge, force push e exclusão bloqueados, e nenhum bypass para os GitHub Apps da fábrica.

Enquanto ele não existir, deixe o Desenvolvedor pausado. Em Settings → Rules → Rulesets do repositório, crie um ruleset de branch com enforcement Active, alvo refs/heads/main, marque Require a pull request before merging (zero aprovações bastam: uma pessoa continua fazendo o merge), Block force pushes e Restrict deletions, e não ponha ninguém na lista de bypass, para que nenhum App da fábrica consiga pular as regras. Sem bypass vale também para pessoas: a mudança de uma pessoa, inclusive o commit de changelog de uma release, chega ao main por pull request, e a tag da release vai no commit do merge (o ruleset vale para refs/heads/main, não para tags). Ou pela API, trocando <owner>/<name>:

O Merger faz merge, então antes de ele começar o main exige também os checks que o merge_if_ready dele espera (#207):

Antes de iniciar o Merger, o main precisa ter também o ruleset de checks: os seis checks do workflow check exigidos do GitHub Actions num head atualizado, e nenhum bypass para ninguém.

É um segundo ruleset, ao lado do mínimo. Ele exige os seis jobs do workflow check, com os nomes que o GitHub mostra — go, postgres, console, chart, factory-mcp-image, artifact, exatamente o FACTORY_CHECKS do Merger —, cada um vindo do GitHub Actions (app id 15368), porque só o nome de um check não prova nada; em modo strict, para que o head contenha a base atual; e ninguém tem bypass:

O factory/qa e a aprovação do Revisor não estão em nenhum ruleset: o merge_if_ready exige os dois no head. Exigido sem bypass, o factory/qa bloquearia todo pull request que não passa pela fábrica, e um ruleset não consegue apontar um GitHub App como revisor obrigatório.

3. Registre os servidores de ferramentas uma vez por papel

Section titled “3. Registre os servidores de ferramentas uma vez por papel”

Na administração, registre o GitHub MCP hospedado (https://api.githubcopilot.com/mcp/) cinco vezes, uma por papel, com o id github-<papel>: github-triage, github-architect, github-reviewer, github-qa, github-developer. Escolha a credencial GitHub App e preencha o App daquele papel (veja MCPs e credenciais, seção “GitHub App”).

Os toolsets padrão do servidor hospedado não incluem projects, então preencha o campo Toolsets (enviado como X-MCP-Toolsets) em todos os registros:

PapelToolsets
Triagemissues,projects
Arquitetoissues,projects,repos
Revisorpull_requests,repos,issues,projects
QApull_requests,repos,issues,projects
Desenvolvedorpull_requests,repos,issues,projects

O servidor hospedado ignora em silêncio um nome de toolset que não conhece, então um erro de digitação só aparece depois, como uma publicação recusada por falta de ferramentas.

Os toolsets oferecem mais do que um papel declara — o conjunto projects também oferece o projects_write, que altera qualquer campo de qualquer card e apaga cards, e que nenhum papel tem. Assim que um servidor responder, abra a página Ferramentas e superfície dele e traga exatamente estas ferramentas, nada além. Uma ferramenta deixada fora da superfície não existe para os agentes: um papel que a cita é recusado na publicação, e uma chamada a ela é recusada.

ServidorFerramentas dele
github-triageprojects_list,projects_get,issue_read,list_issues,search_issues,add_issue_comment,issue_write
github-architectprojects_list,projects_get,issue_read,search_issues,get_file_contents,search_code,list_commits,get_commit,add_issue_comment,issue_write
github-reviewersearch_pull_requests,pull_request_read,issue_read,get_file_contents,search_code,get_commit,pull_request_review_write,issue_write,add_issue_comment,projects_list,projects_get
github-qasearch_pull_requests,pull_request_read,issue_read,get_file_contents,issue_write,add_issue_comment,projects_list,projects_get
github-developersearch_pull_requests,projects_list,projects_get,issue_read,pull_request_read,get_file_contents,search_code,get_commit,create_branch,create_or_update_file,push_files,create_pull_request,add_issue_comment,issue_write

O servidor hospedado também pode ser estreitado do lado dele: o header X-MCP-Tools com uma linha acima, e sem X-MCP-Toolsets, faz ele listar só essas ferramentas (com os dois preenchidos, as ferramentas são somadas aos conjuntos). O painel do App no console só preenche Toolsets, então esse header é gravado pela API de administração; a superfície é obrigatória de qualquer jeito.

O servidor da própria fábrica

Section titled “O servidor da própria fábrica”

O servidor da fábrica roda como sidecar em cada pod do worker, em http://127.0.0.1:8091/, sem credencial própria: o token de App de cada requisição diz qual papel está chamando, e ele só serve as ferramentas desse papel. Como implantá-lo, e o ConfigMap que ele lê, estão em factory/mcp/README.md. Antes do primeiro worker subir com ele, confira que a imagem pode ser baixada sem credencial:

A resposta precisa ser public; se não for, dê ao worker um pull secret do GHCR.

Depois registre-o mais seis vezes, com o id factory-<papel>: factory-triage, factory-architect, factory-reviewer, factory-qa, factory-developer, factory-merger. A URL é http://127.0.0.1:8091/ (http:// sem TLS só é aceito ao lado de um GitHub App para loopback), a credencial é GitHub App, e o App é o mesmo do github-<papel> daquele papel. Não preencha toolsets. Cada registro então oferece as ferramentas do seu papel:

ServidorFerramentas
factory-triage, factory-architectmove_card, set_card_fields
factory-developer, factory-reviewermove_card
factory-qamove_card, record_qa_verdict
factory-mergerlist_ready_prs, merge_if_ready, send_back, move_card, close_merged

Um registro que não oferece nada, ou que oferece outra linha, recebeu o App errado.

Rode o canário do operador antes de iniciar qualquer papel. Nenhum teste prova o que o GitHub faz com um token restrito a um repositório, então, uma vez por App de papel, com um token assim, rode as três chamadas do canário de setup contra um card descartável: a consulta viewer { databaseId } precisa responder o id do bot daquele papel, a consulta do item precisa devolver o projeto e o Status do card, e a mutação que move precisa responder o item sem erros. Com o token do QA, comente e coloque um rótulo também num pull request descartável pela API de Issues (o quarto passo do canário): o App do QA só tem Pull requests: read, e é isso que comprova que o Issues: write basta para o que o QA escreve ali. Com o token do Merger, coloque um rótulo e comente também num pull request descartável: o App dele não tem permissão de Issues, e isso comprova que o Pull requests: write basta para o que o send_back escreve. Um papel cujo canário falha continua parado.

4. Classifique as ferramentas

Section titled “4. Classifique as ferramentas”

Com cada servidor respondendo, classifique todas as ferramentas que os papéis declaram (veja O que a plataforma para antes de acontecer).

Toda ferramenta de leitura é não confiável (untrusted) — não só as que leem o corpo de uma issue. Uma listagem devolve texto escrito por pessoas: o projects_list devolve os títulos das issues e pull requests do board mesmo quando não se pede nenhum campo (#220).

Classifique comoFerramentas
read, untrustedprojects_list, projects_get, search_pull_requests, search_issues, list_issues, issue_read, pull_request_read, get_file_contents, search_code, list_commits, get_commit
writeadd_issue_comment, issue_write, pull_request_review_write, create_branch, create_or_update_file, push_files, create_pull_request
write, resultado não untrustedmove_card, set_card_fields, record_qa_verdict, send_back, close_merged, nos servidores factory-<papel>
read, resultado não untrustedlist_ready_prs, no factory-merger
destructivemerge_if_ready, no factory-merger

Classifique cada ferramenta no servidor de cada papel: github-triage.projects_list e github-reviewer.projects_list são entradas separadas. O issue_write também é como o Arquiteto cria uma sub-issue embaixo da issue do card, então ele continua sendo write no github-architect.

O toolset repos do Arquiteto também oferece escritas de arquivo e de branch, e nenhum header tira essas ferramentas no mesmo servidor: o X-MCP-Readonly tiraria também as escritas em issues. A referência dele não declara nenhuma delas, e o Contents: read do App dele as recusa.

As ferramentas da fábrica só respondem estado estruturado — motivos de um conjunto fechado, nomes de coluna e de campo, números, SHAs de commit —, nunca texto que alguém escreveu no GitHub, então o resultado delas não é untrusted. Mesmo assim são escritas: uma pessoa aprova cada card movido, cada campo e cada veredito do QA.

As duas linhas do Merger importam mais que todas as outras. O list_ready_prs precisa ser classificado como não untrusted: é a única leitura do Merger, e no padrão untrusted ela contaminaria todo run do Merger antes do merge, e o Gate nunca deixa um efeito irreversível derivar de dado não confiável, então todo merge seria bloqueado.

O merge_if_ready é destructive, o que o Gate bloqueia por padrão, e a aprovação de uma pessoa nunca libera um bloqueio. Salve esta política antes de o Merger começar, em Políticas no console — código FACTORY-MERGE, ferramenta factory-merger.merge_if_ready, efeito destructive, alcance o agente factory-merger, ação escalate, modo enforce — ou pela API, com os mesmos campos:

Mantenha-a exatamente assim, estreita: uma ferramenta *, ou um alcance da instalação inteira, tornaria aprovável toda ferramenta destrutiva, não só esta (veja Políticas).

Inicie o Merger só depois que a política FACTORY-MERGE estiver salva e em enforce; sem ela, o Gate bloqueia todo merge e nenhuma aprovação o libera.

Deixe o projects_write sem classificação. Nenhum papel o declara, ele fica fora de todas as superfícies, e uma ferramenta sem classificação nunca executa.

5. Crie a área da fábrica

Section titled “5. Crie a área da fábrica”

Crie uma área para a fábrica, para que custo, orçamento e concessões dela fiquem separados de todos os outros agentes, e dê um orçamento a ela (veja Custos e limites e Empresas, áreas e papéis). As referências usam o id de área factory.

6. Crie os papéis

Section titled “6. Crie os papéis”

Para cada papel, crie o agente no Studio a partir da referência: os campos do frontmatter, e o corpo como instruções.

  • Triagem
  • Arquiteto
  • Revisor
  • QA
  • Desenvolvedor
  • Merger

Depois publique — um agente novo é um rascunho pausado —, ponha o estágio em copiloto e inicie. O estágio não está no arquivo, então ele sempre é definido no console. Só inicie o Desenvolvedor depois que o main tiver o ruleset mínimo, e o Merger depois que ele tiver também o ruleset de checks e a configuração do sidecar listar o Merger (passo 2; factory/mcp/README.md).

O console recusa publicar uma ferramenta que o servidor registrado não oferece, então um nome de ferramenta errado, ou um toolset faltando, aparece aqui, e não na hora do run.

O que os papéis seguem está no mesmo diretório: RULEBOOK (as regras que todo papel segue), REVIEW (o formato da revisão) e LANES (o que significa pronto em cada coluna e rótulo). O README das referências explica cada linha de uma referência.

O que o Arquiteto faz

Section titled “O que o Arquiteto faz”

O Arquiteto pega o card mais antigo da coluna Triagem com o rótulo factory:needs-design, que a Triagem deixa para ele. Ele confere no código cada afirmação sobre o código, só com ferramentas de leitura, e escreve o plano e os critérios de aceite num comentário na issue: o corpo da issue continua sendo de quem pediu, e um plano novo é um comentário novo, não uma edição. Um item grande é dividido em sub-issues, criadas embaixo da issue do card. Depois:

  • sem nenhuma decisão em aberto, ele tira o factory:needs-design e move o card para Preparado, de onde uma pessoa o puxa para Doing;
  • quando uma decisão cabe ao dono, ele escreve o plano até ali e cada decisão em aberto como pergunta, mencionando com @ quem decide para que o GitHub avise essa pessoa, e move o card para Travado mantendo o rótulo, para que o card volte para ele quando a pergunta for respondida e quem opera o board o devolver para Triagem, como diz a última linha do comentário (abaixo);
  • se uma sub-issue, o rótulo ou a movimentação não puder ser gravado, ele diz qual na issue e move o card para Travado, para que o card não seja escolhido de novo a cada hora.

Ele nunca escreve código, nunca abre branch nem pull request e nunca planeja uma mudança em factory/ ou nos arquivos CLAUDE.md. O App dele não precisa de ruleset no main antes de começar: com Contents: read, ele não consegue escrever lá.

O que o Desenvolvedor faz, e o que fica esperando

Section titled “O que o Desenvolvedor faz, e o que fica esperando”

O Desenvolvedor trabalha no Nível 1: mudanças pequenas e autocontidas, feitas pela API do GitHub, sem build e sem rodar testes antes do pull request — uma correção de documentação ou de configuração, uma renomeação mecânica, um patch num arquivo só, a versão fixada de uma dependência cujo arquivo de lock não precisa de ferramenta para ser gerado de novo. Quando há código envolvido, ele faz primeiro o commit do teste e abre o pull request nesse commit, para que o CI mostre o teste falhando antes da mudança. Ele põe o rótulo factory:needs-review no pull request e, quando a revisão o devolve com factory:changes-requested, responde a cada apontamento com um commit e um comentário.

Um card que precisa de um build ou de rodar testes antes do pull request não é tentado. O Desenvolvedor põe o rótulo factory:needs-runtime na issue, explica o motivo num comentário e deixa o card em Doing para uma pessoa. Se o rótulo não puder ser aplicado, porque nunca foi criado (passo 1), ele avisa e move o card para Travado, para que o card não seja escolhido de novo a cada hora. O Nível 2, build e testes antes do pull request, virá de um runtime de código atrás de uma única ferramenta MCP: o runtime previsto é o FuseOne Forja, um projeto à parte, ainda na fase 0 proposta, com forja.implement como ferramenta de escrita sob o Gate.

Quem tira um card de Travado

Section titled “Quem tira um card de Travado”

Nenhum papel tira um card de Travado, e resolver o que o travou também não move o card. Na primeira versão isso é uma tarefa fixa de uma pessoa, dada a quem opera o board:

Quem opera o board revisa a coluna Travado todo dia útil e, quando o bloqueio indicado no comentário que travou um card é resolvido, devolve o card para a coluna que esse comentário indica, Triagem ou Doing, sem mexer nos rótulos; esse comentário é o mais recente do GitHub App do papel que travou o card que termina com uma linha Return to:, na issue ou no pull request em que o papel trabalhou, sendo o pull request o próprio card ou o que aparece no campo Linked pull requests do card.

Um card não volta para nenhuma coluna quando o item que ele representa terminou: quem opera o board o move de Travado para Done quando o card é uma issue fechada, ou um pull request com merge feito ou fechado.

Um pull request fechado sem merge enquanto a issue do card continua aberta não encerra o card: ele volta para a coluna indicada pela linha Return to:, e uma pessoa começa a próxima tentativa, já que o Desenvolvedor pula um card que tem pull request vinculado.

A Triagem e o Arquiteto escrevem esse comentário na issue do card; o Revisor, o QA e o Desenvolvedor, quando responde a uma revisão, escrevem no pull request, que é o próprio card ou o que aparece no campo Linked pull requests do card. A última linha desse comentário é fixa: Return to: Triagem quando quem travou o card foi a Triagem ou o Arquiteto, Return to: Doing quando foi o Desenvolvedor, o Revisor ou o QA. Um card que volta para Triagem ainda com factory:needs-design é retomado pelo Arquiteto; um card que volta para Doing mantém o rótulo do pull request, e o papel indicado por esse rótulo o retoma.

O papel que travou o card diz nesse comentário o que bloqueia o card e o que uma pessoa precisa fazer para resolver — responder a uma pergunta, criar um rótulo que falta, dizer se um plano pela metade deve ser retomado ou descartado —, nunca só o que aconteceu. É essa ação que impede o papel de travar o card de novo no próximo run; quem opera o board é quem percebe que ela foi feita. O LANES lista cada caminho para Travado e a ação de cada um. Sem alguém nessa tarefa, um card travado fica esperando para sempre.

Por papel, por semana

Section titled “Por papel, por semana”

A tela Item de trabalho (/work-items), aberta sem nenhum card, mostra Por papel, por semana: o que o registro das execuções sabe sobre o trabalho da fábrica, uma tabela por semana ISO (segunda-feira, 00:00 UTC), a mais recente primeiro. A semana atual vem marcada como parcial. Escolha 4, 8, 12 ou 26 semanas e, se quiser, uma só área ou um só papel. O histórico de um card continua abrindo pelo link Item de um claim.

Cada linha é um papel numa semana, contando os runs abertos naquela semana:

  • Execuções: os runs abertos, com quantos ainda estão em andamento ao lado.
  • Itens: os cards distintos que os runs assumiram, com um pull request vinculado contado como a sua issue. Um run que só está num card porque um evento ou uma entrega do GitHub o abriu não acrescenta card.
  • Aprovações pedidas, Aprovadas, Recusadas, Pendentes, Abandonadas: o que os runs pediram às pessoas e como elas responderam. Ao lado de Aprovadas e Recusadas fica a parte delas entre as decididas (aprovadas mais recusadas).
  • Revisadas após recusa e Repetidas após recusa: recusas depois das quais o mesmo run propôs a mesma ferramenta de novo com outros argumentos, ou com os mesmos, ao lado da parte delas entre as recusas.
  • Permanentes: aprovações dadas por uma aprovação permanente. Todo papel da fábrica declara standing_approvals: forbidden, então para eles o número deve ser 0. Uma linha com alguma, de um agente cuja definição publicada as proíbe, vem marcada com A política do agente proíbe aprovações permanentes. Para um agente que as permite, é só uma contagem.
  • Em itens, Herdado, Fora de item: para onde foi o custo — runs que assumiram um card, runs que só estão num card pela forma como foram abertos, e runs sem card. Por item é o custo em itens dividido pelos itens.

Uma taxa sem base mostra um traço, nunca 0 %, e o mesmo vale para Por item numa semana sem card. Sem cost:read sobre a linha, todo custo mostra um traço, nunca R$ 0.

Abaixo das tabelas, Fora destas contas diz em palavras o que este painel não consegue medir. A edição de propostas não é registrada pela plataforma: uma decisão aprova ou recusa a proposta como ela foi pedida, então as contagens de revisadas e repetidas são o que o registro tem no lugar. O tempo em lane e os achados posteriores vêm do quadro do projeto e são lidos pela CLI da fábrica, não por esta tela.

Essa CLI é a factory/measure. Ela lê o quadro e as timelines das issues e dos pull requests dele, não grava nada no GitHub e imprime as mesmas semanas em markdown: a mediana e o p90 de horas de cada lane, o tempo que ficou com cada papel e com cada pessoa, e os sinais pegos depois. Antes de confiar em um relatório, rode o canary dela com o token que você vai usar. Enquanto ele não passa, ninguém confirmou que o GitHub mostra os movimentos de um papel como sendo do App desse papel.

Mudando um papel

Section titled “Mudando um papel”

Uma mudança num papel é feita primeiro na referência, revisada por pull request, e depois copiada para o console. Quando o console e a referência discordam, foi o console que se desviou.

Depois de mudar os toolsets de um registro, confira se o servidor aparece como alcançável antes de confiar numa publicação. A próxima descoberta substitui as ferramentas dele: uma ferramenta que os toolsets novos não oferecem sai do catálogo, e a checagem da publicação recusa um papel que ainda a cita. Um servidor que não pode ser alcançado mantém as ferramentas da última descoberta bem-sucedida, então, até ser alcançado de novo, o catálogo ainda mostra o conjunto antigo.
