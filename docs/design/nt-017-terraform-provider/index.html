NT-017 — A Terraform provider for FuseOne Agents

Status: proposed · 2026-11-11 · builds on #212 (service accounts) and #268 (read-back and If-Match) · issue #270

What this is

Section titled “What this is”

Installations that manage their platform with Terraform want to manage FuseOne Agents the same way: an area, who works in it, the tool servers it reaches, how each tool is classified and the agents that run there, all reviewed in a pull request beside the rest of their infrastructure.

This note specifies a Terraform provider for that, and the changes the API needs first. It widens #270, whose first cut was five integration resources. The request in practice is “everything an administrator configures”, so the note covers that, in three phases, and says for each resource what the API lacks today.

Who does what. An administrator writes the configuration and runs terraform plan and apply with a service-account token. A person creates that service account, gives it roles and issues its token; the provider never does. Nothing the provider does puts an agent to work, changes its autonomy stage or releases an approval. The provider is a client of the public API and nothing else: if it needs something the API lacks, the API gets it, for every client.

What is already decided

Section titled “What is already decided”

From #270, #212, #268 and the review of this note’s scope:

  • Public API only. Types come from api/openapi.yaml at a released tag, so the provider and the server cannot drift apart unnoticed.
  • Bootstrap stays with a person. No token can hold identity:write, so the provider creates no service accounts, tokens or identity providers.
  • Starting things stays out. No apply changes an agent’s stage, resumes it, or releases anything the Gate held. The one exception is explicit: destroying an agent retires it, which pauses it, and the plan shows that as a retirement (see Agents).
  • Console edits are drift. A person may still change these resources in the console. The next plan shows the change; it is not silently overwritten.
  • Secrets never reach the state file.
  • Wider scope, three phases, decided 2026-11-11: what the API already supports, then companies, areas and classification, then access to an area.
  • Access may be delegated under four rules (see Access), decided 2026-11-11, the same rules for people and tokens. The only role delegation grants is author. identity:write stays barred for tokens.
  • Repository: fuseone-io/terraform-provider-fuseoneagents, so resources are named fuseoneagents_mcp_server, fuseoneagents_agent and so on.

Every row except grants is writable by a service account with the right role today (internal/domain/access.go, Principal.barredFrom in internal/domain/principal.go).

Four things hold for every resource and shape the provider:

  1. Omitting an optional field keeps the stored value. Removing an attribute from the configuration clears nothing on the server, so the provider sends each resource’s explicit clear (clearToken, an empty object, an empty list) when an attribute leaves the configuration.
  2. Some values come back normalised. An omitted MCP transport reads back stdio, a cache maxEntries of 0 reads back 256, a policy resource of "" reads back *, lists are trimmed and deduplicated. Each one is a default or a plan modifier in the provider’s schema, or the plan never settles. The provider’s acceptance tests find them: an unchanged configuration must plan empty right after apply.
  3. Deleting something missing answers 204. The provider detects removal by the read, which answers 404.
  4. Four of the five integration writes answer 204 with only an ETag. The provider reads after each write to fill its state.

Phase 1: what the API already supports

Section titled “Phase 1: what the API already supports”

Resources: mcp_server, connector_instance, model_provider, channel, policy, agent. Data sources: agents, connector_catalog, mcp_recipes.

Servers and providers configured by flag or environment variable come back with managed: false. The provider refuses to import or manage them: their source of truth is the deployment, not the API.

Concurrency

Section titled “Concurrency”

The provider stores the ETag from its last read and sends it as If-Match on every update and delete. A 412 is a person having changed the resource since the plan; the provider reports it and tells the operator to plan again. It never retries without the header.

Every create sends If-None-Match: *. Without a precondition a create is a blind write. If-Match: * means “it exists”, and without either header the last write wins (api/openapi.yaml:5026-5031). So a resource somebody created in the console between plan and apply would be overwritten by the apply, with nobody seeing it. No write in the API takes If-None-Match today: the only use is the read of brand assets (internal/httpapi/brand_asset.go:113). Phase 1 adds it to every PUT that can create: the integrations, policies, and the agent’s first version. Phase 2 adds it for companies, areas and classifications, and phase 3 for grants.

  • Exactly one of If-Match and If-None-Match: *. Both, or If-None-Match with any value other than *, is a 400, as for the workbench’s activation (NT-018).
  • Judged under the same guard as If-Match, inside the transaction that writes. For settings-backed resources that is the guard admin/write.go runs first in the transaction (internal/admin/write.go:51-54). For the agent it is the event graph lock publication takes (internal/spec/event_graph_lock.go:30). A check made by an earlier read would leave the window it exists to close.
  • A resource that exists answers 412 with its ETag. The provider says the resource already exists and that the way to manage it is terraform import. It never retries as an update.
  • The agent’s first version. If-None-Match: * on PUT /agents/{id}/versions means no version of that agent id exists. It is judged under the event graph lock in the publish’s transaction, so two first applies of the same id cannot both create it.

Secrets

Section titled “Secrets”

Secrets are write-only attributes, available in Terraform 1.11 and OpenTofu 1.11: they are sent and never stored in the plan or the state. Each one pairs with a <name>_wo_version attribute that is stored, because a write-only value cannot be compared; changing the version is how the configuration says “send the secret again”.

The API already never returns a secret. Only one schema field says so (MCPGitHubApp.privateKey is writeOnly: true); the others say it in prose. Phase 1 marks every secret field writeOnly in api/openapi.yaml, so a client generated from it, the provider included, knows which fields they are.

Integrations by scope (NT-019)

Section titled “Integrations by scope (NT-019)”

After NT-019 an MCP server, connector instance, model provider, channel connection or conversation belongs to the scope it is stored at: the installation, a company or an area.

  • Every integration resource takes scope: installation, <company> or <company>/<area>. It is required, recorded in the state, and read back. Changing it forces a replacement, because the stored key includes the scope. The delete half of that replacement meets the in-use check below like any other delete.
  • Import takes the scope and the name: <scope>:<name>, such as acme/cx:jira. Names are unique per kind across the installation (NT-019’s index), but the reads are not all keyed by name alone. A connector instance’s GET takes its scope as query parameters (scopeKind, company, area). One form for every kind keeps import from depending on a lookup across scopes. A row not found at that scope fails the import, and names nothing of other scopes.
  • A taken name answers 409 fuseone:integration-name-taken. The provider says the name is in use and never by whom, as the server does.
  • Reading needs what NT-019 says. Configuration reads need provider:write at a scope that contains or governs the row (NT-019, rule 4). A service account managing an area gets the role on that area.
  • Each kind accepts a scope other than installation only once its writers’ release is deployed, which NT-019 ships after its readers’ release has reached every replica. The provider learns the server’s version from GET /api/v1/readyz at configure time. A plan that puts a kind at company or area scope on a server older than that kind’s writers’ release fails at plan time, naming the kind and the release it needs. It is never sent and refused halfway through an apply.

Agents

Section titled “Agents”

An agent is published with PUT /agents/{id}/versions. The version is the digest of the rendered definition, and publishing identical content is a no-op, with one exception:

  • A version published before 0.103.0 has no recorded digest. Its claim is NULL (NT-018, releases C1 and C2). Publishing its identical bytes again answers 409 fuseone:version-digest-unknown (api/openapi.yaml:585), and so does landing on any id claimed without a digest. It is refused, not a no-op. A definition whose 48-bit id lands on another definition’s claim answers 409 fuseone:version-collision (api/openapi.yaml:583).

  • Import is unaffected. It reads the agent, and an unchanged configuration plans empty, so nothing is published.

  • Rolling a configuration back to the exact text of a version published before 0.103.0 is refused with version-digest-unknown. Planning again does not help. The provider’s diagnostic says that the version predates recorded digests, and that a change to the definition almost always gives it another id. The id is 48 bits of the digest, so the change may instead land on another claim. That is refused the same way, never resolved silently, and the definition is changed again, as NT-018 decided. The diagnostic names the agent and the version, and the provider does not retry.

  • A collision gets the same treatment: the diagnostic says the definition must change, and the provider never retries.

  • Managed: the definition fields AgentDefinition accepts. The state also records the agent’s ETag from the last read.

  • A precondition, which the API lacks today. Neither PUT /agents/{id}/versions nor PUT /agents/{id}/retired takes If-Match, so a version published in the console between plan and apply would be replaced without anybody seeing it. Phase 1 gives the agent an ETag and makes both calls honour If-Match:

    • The ETag covers the current version and whether the agent is retired, the two things these calls change. A publish moves it; an identical publish does not.
    • If-Match is judged under the agent’s row lock, in the transaction that writes the version or the retirement, where refuseIfStage is already judged. A check made by an earlier read would leave the same window it exists to close.
    • A stale tag answers 412 with the current ETag, as the other resources do.

  • Authorized under the lock, before any precondition is judged. Today the publish authorizes only the destination the body names, before the transaction, and never reads the agent’s current scope (internal/httpapi/publish.go:66-76). Retiring and restoring read and authorize the current scope before the transaction too, and answer 403 (internal/httpapi/retire.go:38-53). An agent moved between that check and the write would be changed under an authority judged on another scope. A 412 judged first would also tell a caller outside the agent’s scope that it exists. Phase 1 orders every publish, retirement and restore the same way, inside the transaction:

    1. Headers, by syntax only. A malformed If-Match or a forbidden combination is a 400 that depends on nothing stored.
    2. The event graph lock, then the agent’s row, in publication’s order.
    3. The current scope, read under the lock. If the agent exists and the caller does not hold agent:publish there, the answer is 404, as for an agent that does not exist.
    4. The destination, for a publish: agent:publish on the company and area the body names (publishScope, internal/httpapi/publish.go:237-253). The caller chose it, so a refusal is the 403 it is today.
    5. Only then the precondition: If-Match, or If-None-Match: * for a first version. A 412 is therefore never answered before both scopes are authorized.

    Moving an agent to another area is a publish with a new destination. It needs agent:publish on both.

  • Drift: a read whose ETag differs from the recorded one means somebody published or retired since, and the plan shows it.

  • Read-back gap: GET /agents/{id} does not return the rendered definition, and the provider needs every field it manages to come back. Phase 1 checks which AgentDefinition fields AgentDetail lacks and adds them to the read, rather than the provider keeping its own copy.

  • Never on an unsupervised agent. Every publish sends refuseIfStage=autonomous. The stage is judged under the agent’s row lock, so a promotion that lands while the apply runs is seen and the publish is refused with 409 fuseone:stage-refused. Changing what an autonomous agent runs stays a person’s decision in the console.

  • A new agent is paused. Authoring starts nothing, so a first apply puts nothing to work.

  • destroy retires, and that is the one exception to “nothing pauses”. Versions are the only explanation of the runs that used them, so the provider retires the agent (PUT /agents/{id}/retired, with If-Match), which pauses it and is reversible. The plan says retire, not delete, so the reviewer of the pull request sees that the agent stops. The OpenAPI text for retiring promises a line in the trail, and none is written today. Phase 1 writes it.

Deleting what something depends on

Section titled “Deleting what something depends on”

No resource refuses a delete today. Deleting an MCP server removes its tools from the catalogue, and the agents that used them stay published, naming tools that no longer exist; only a new publish is checked against the catalogue.

Phase 1 makes DELETE on an MCP server, connector instance or model provider answer 409 fuseone:in-use while the current version of an agent that is not retired refers to it. The console gets the same answer.

The problem names only the agents the caller may read. Whoever deletes an integration governs it, and governing an integration grants no agent:read on the areas whose agents use it. An administrator at default/platform does not read acme/cx’s agents. So the problem carries two fields:

  • agents: the blocking agents in a scope where the caller holds agent:read;
  • hidden: how many others there are, as a count, never as ids or scopes.

The delete is refused on the whole set, readable or not. Filtering the set before judging would let the delete pass whenever the blocking agent is one the caller cannot see. Channels and policies are not covered: an agent definition names neither (a channel names agents, not the other way round), and deleting a policy already takes a new snapshot.

The check needs a lock both sides take. Today the publish judges the catalogue before the transaction that writes the version (internal/httpapi/publish.go, rulingsFor), and the delete runs in a transaction of its own (RemoveMCPServer in internal/admin/integrations.go). A publish and a delete running together can both pass their checks and leave an agent naming something that is gone. Phase 1 closes it by locking the row of the resource itself, first, then judging:

  • The delete takes FOR UPDATE on the resource’s row before anything else, then looks for referring agents in the same transaction.
  • The publish takes FOR SHARE on the row of every resource the definition names (the servers and connector instances behind its tools, its model provider, its area), in the transaction that writes the version, and judges existence after the lock is granted. Today the publish does not check the model provider at all; phase 1 adds that check, or the fence would hold on one side only.
  • Restoring a retired agent takes the same lock. The delete is allowed once the agents using a resource are retired, and PUT /agents/{id}/retired with retired: false brings one back without publishing, so restoring is a third way to make an agent refer to something. Today it only clears retired_at (State.Restore in internal/spec/retire.go). Phase 1 makes it take FOR SHARE on every resource the current version names, in the transaction that judges If-Match and changes retired, and judge existence after the lock. If any is missing, it does not restore and answers 409 naming what is missing; the person publishes a version that does not need it, which goes through the publish’s own check.
  • Whichever commits first wins, and the other sees it: a delete that waited finds the new version or the restored agent and answers 409; a publish or a restore that waited finds the row gone and is refused.
  • Servers and providers configured by flag or environment variable have no row to lock, and the API cannot delete them either.

No force flag. An emergency, such as a compromised MCP server, goes in this order:

  1. Disable the resource (enabled: false) and revoke or rotate its credential. Both are updates, not deletes, and the 409 never applies to them.
  2. Edit or retire the agents that use it.
  3. Delete it.

The manual documents the order, and a test proves the 409 does not block step 1.

Phase 2: companies, areas and classification

Section titled “Phase 2: companies, areas and classification”

The API gains what the provider needs, for every client.

Companies. GET /admin/companies/{company} and PUT /admin/companies/{company}, idempotent, with ETag and If-Match. A company is never deleted: destroy archives it, and applying it again restores it, which the existing archived flag already models. Creating a company still grants the creator curator on it.

Areas. GET and PUT /admin/scopes/{company}/{area}, idempotent, with ETag and If-Match. Two gaps close at the same time:

  • Registering and deleting an area write nothing to admin_events today. Both will.
  • Deleting an area leaves the agents, ceilings and policies that name it in place. Today it is a bare delete from scopes (internal/scope/store.go:163-174). The delete answers 409 fuseone:in-use while an agent that is not retired is published there, behind the same fence as phase 1: the delete takes FOR UPDATE on the area’s row first, and the publish already holds FOR SHARE on it.
  • After NT-019 an area also holds configuration: connector instances, MCP servers, model providers, channel connections, conversations, and owner classifications stored at that area. Leaving them behind would orphan sealed credentials and tools under an area nobody can see or administer. So the delete refuses with 409 fuseone:in-use while any settings row is stored at that area, whatever its kind.

    • The same fence. Every write of a settings row at area scope takes FOR SHARE on the area’s row in its transaction, and refuses a write into an area that is not registered. The delete holds FOR UPDATE first. Whichever commits first wins, and the other sees it.

    • Such writes exist today. Connector instances are written at area scope (connectorScopes, internal/admin/connectors.go:41-59), and so are conversations (internal/admin/channels.go:577-579) and budgets (internal/admin/budgets.go). None of them reads scopes, so today a row can be written into an area that is not registered, or is being deleted.

    • Fence first, door a release later, so the guarantee holds against the previous binary:

      1. The fence release. Every area-scoped settings write takes the area’s FOR SHARE and refuses an unregistered area. The area delete stays as it is today. Nothing a person does changes, except that a write into an unregistered area is now refused with 400.
      2. The delete release, shipped only after the fence release runs on every serve and worker replica. It adds the FOR UPDATE, the in-use check over agents and settings rows, and the 409.

      A replica older than the fence release writes area rows without the lock. If it ran beside the delete, it could write into an area the delete just removed. So the delete release states a rollback floor: once it is deployed, never below the fence release. Rolling back from the delete release to the fence release is safe, because the fence release takes the lock and only lacks the door.

    • The problem lists, per kind, the names the caller may read under NT-019’s listing rule, and a count of the others, as for agents above.

    • No cascade. An area’s configuration is removed resource by resource, through each resource’s own delete and its own in-use check. Removing them all at once would bypass those checks.

The PUT takes the area id as given. Today’s POST folds a name into an id (lowercase, no accents, hyphens); a provider resource keyed by a folded value would plan a replacement every time. The PUT refuses an id that folding would change, and the POST stays as the console’s convenience.

Tool classification. GET /admin/tools/{id}/classification?level=…, ETag and If-Match on the PUT, and an identical PUT becomes a no-op. Its identity is the pair (tool, level), level being owner or platform (NT-019, Classification under the platform’s ceiling):

  • fuseoneagents_tool_classification takes level, which forces a replacement when it changes. Two resources may classify one tool, one per level, and they are two rows.
  • Precedence is the server’s. The platform’s row wins, the owner’s applies only without it, and a stale ruling never falls back to the other row. The provider does not resolve it. A data source exposes the effective ruling and its level, so a plan can show that an owner’s ruling is overridden.
  • Destroying the platform level is NT-019’s withdrawal of the ceiling (DELETE with level: platform). Destroying the owner level needs a DELETE with level: owner, which NT-019 does not define. This note adds it, under tool:classify at the server’s authorization scope, and it removes the owner’s row only.
  • For a server of the installation, the two levels are one row, and only level: platform is accepted. Today every write records a tool.classified event, so an unchanged apply would add a line to the trail each time.

The classification carries the digest of the tool definition it was judged against, and the provider makes digest a required attribute. A curator approving a tool approves one definition; if the provider filled in whatever digest is current, a server that changed its tool would be approved by the next apply with nobody reading it. When the definition changes, the plan shows the mismatch and a person updates the digest in a pull request. A data source exposes the current digest to read from.

Two consequences, documented rather than hidden:

  • A tool exists only after its server is discovered, which workers do asynchronously. Adding a server and classifying its tools is two applies.
  • Classifying ahead of discovery without a digest stays possible in the API and the console. The provider does not offer it.

Phase 3: access to an area

Section titled “Phase 3: access to an area”

Today only a person with identity:write on the installation can grant access, and the grant call replaces every hand-set grant a principal holds, including grants other operators made.

Phase 3 adds a grant as a resource of its own:

GET, PUT and DELETE /admin/grants/{principal}/{company}/{area}/{role}

  • PUT and DELETE add or remove exactly one hand-set grant and touch nothing else.
  • GET answers 200 when that hand-set grant exists, with who made it and when, and 404 when it does not. A grant asserted by an identity provider with the same principal, scope and role does not count: the provider manages only what a hand made, and import reads with the same path.

A person with identity:write on the installation may use all three without limits, as today. Every other caller, a person or a service account, goes through the same rules:

  1. Delegation is a permission, held where it is used. The caller holds access:delegate in a grant whose scope contains the target scope. A curator of area X can act in X and not in Y.
  2. The only role it grants is author. An allowlist, not a list of exceptions. Allowing any role whose permissions the caller holds would let a curator create another curator, who receives delegation, policy and provider writes and erasure in turn. admin, approver, curator and auditor stay with identity:write.
  3. Only to a person. Never to itself and never to a service account, so tokens cannot widen each other’s reach.
  4. Recorded. Each grant and revocation writes grants.added or grants.removed to admin_events with the caller’s id, the grant and, for a token, the token’s id. The request context does not carry the token’s id today; phase 3 adds it, so the grants a revoked token made can be found.

The same rules decide a read: a caller may read a grant it could make. A caller may revoke only a grant it could have made, so a delegating caller can remove an author grant in its scope and nothing else. Grants asserted by an identity provider are never touched.

access:delegate goes into the admin and curator roles. It is not barred for tokens; the rules are what make that safe. For people it is new: a curator of an area can now give author there without installation-wide identity:write, which is what “a team looks after its own agent” in the scopes manual needs.

Four facts about grants today shape the resource:

  • A person must have signed in once. A principal row is created at first sign-in, and a grant for a principal that does not exist answers 404.

  • Nobody but identity:write can find a person today. GET /admin/people needs it, so a token cannot turn an email into a principal id. Phase 3 adds an exact lookup by email for a caller holding access:delegate, answering one id or 404 and never a list. That stops listing everybody, but it is still an oracle: a caller with a list of candidate addresses learns which ones have an account. Two mitigations bound it:

    • A rate limit per caller, configurable, with a low default; past it the lookup answers 429.
    • Every lookup is recorded in admin_events: the caller, the time, and the principal id when one was found or found: false when none was. Nothing derived from the address is kept, not even a keyed digest: a stable digest next to the caller’s id would let probes be correlated, which makes it a pseudonym, not an absence of personal data. The row is personal data either way, because it names the caller, and falls under what DP-001 says about admin_events.

    The provider’s person data source uses the lookup, and a plan for somebody who has never signed in fails with that reason.

  • A hand grant equal to an asserted one is dropped today. The key is principal, company, area and role, without the source, and the insert ignores a conflict. The hand grant vanishes when the identity provider stops asserting it, and the provider would report drift it cannot fix. Phase 3 makes the source part of the key, so the two are separate rows.

  • The role and the scope are not checked today. A bad role reaches the database constraint and surfaces as a 500, and a grant for a company or area that does not exist is accepted. The new call refuses both with 400.

Group mappings, which grant access to everybody an identity provider puts in a group, remain identity:write and stay with a person. They grant access to people who have never signed in, which the rules cannot judge.

The provider

Section titled “The provider”
  • Framework: HashiCorp’s terraform-plugin-framework, in Go.
  • Client: generated from api/openapi.yaml at a pinned server release with oapi-codegen in client mode. Bumping the pin regenerates the client, and CI fails if the generated code differs from what is committed.
  • Compatibility: the provider reads the server version from GET /api/v1/readyz at configure time and refuses a server older than the minimum its release names. Breaking changes follow the API’s compatibility statement in automating-configuration.md.
  • Distribution: signed releases on the Terraform registry and the OpenTofu registry. Air-gapped installations get a documented filesystem mirror.
  • Documentation: pt-BR and en-US, with a worked example that builds an area, its MCP server, the server’s classifications and an agent.

Rollout

Section titled “Rollout”

Each phase is a FuseOne release followed by a provider release that requires it.

  • Phase 1’s 409 on delete changes console behaviour too. It ships with the console showing the agents that block the delete.
  • A new If-Match is honoured only by a replica that knows it. The provider’s minimum version covers this for the provider, and the console sends If-Match on a new resource only after a release in which every replica supports it, as in #268.
  • The agent’s If-Match is judged only by a replica that knows it. An old replica ignores the header and publishes, so the provider’s minimum server version is the phase 1 release, and the console sends If-Match on publish and retire only after a release in which every replica supports it.
  • The fence on delete holds only when both sides take the lock. A replica still on the previous release publishes without FOR SHARE, so the 409 is a guarantee only once every replica runs phase 1. Until then it is a check, and the release notes say so.
  • The area delete ships in two releases: the fence, then the door, with the door enabled only once the fence runs on every replica, and a rollback floor at the fence release (see Phase 2).
  • Integration resources follow NT-019’s rollout per kind: readers, then writers. The provider’s support for a scope below the installation is gated per kind on that kind’s writers’ release, as above.
  • If-None-Match: * is honoured only by a replica that knows it. An old replica ignores the header and writes, so the provider’s minimum server version is the release that adds it, and the guarantee holds once every replica runs that release.
  • access:delegate is a new permission in a role. Rolling back below phase 3 removes it, and the grants it made stay valid: they are ordinary grants.

What this is not

Section titled “What this is not”
  • Not a way to create service accounts, tokens or identity providers.
  • Not a way to change an agent’s stage, resume it or approve anything. Destroying an agent retires it, which pauses it; that is the one exception, and the plan names it.
  • Not custom roles. The five roles cover the cases asked for; an editable permission matrix is a separate feature.
  • Not a replacement for the console. Both write the same resources, and the plan says when they disagree.

Tests that must exist

Section titled “Tests that must exist”

Server side, each written before its change:

  • A DELETE of an MCP server used by an agent that is not retired answers 409 and lists it; once the agent is retired, the delete succeeds. The same for a connector instance, a model provider and, in phase 2, an area.
  • enabled: false and a credential rotation on a resource in use succeed: the 409 never blocks the first step of the emergency order.
  • Publish and delete racing, in both orders, for an MCP server and for an area. Each side is held at its lock with a test hook, the other runs, and the outcome is either a 409 on the delete or a 400 on the publish, never both succeeding.
  • Restore and delete racing, in both orders, the same way: either the delete answers 409 or the restore is refused, never both succeeding.
  • Restoring an agent after a resource its current version names was deleted is refused, and the agent stays retired.
  • A publish naming a model provider that does not exist answers 400.
  • A publish with a stale If-Match answers 412 and writes no version; the same for a retirement. A publish landing between the read and the write with the old tag is the case the test uses, not a made-up tag.
  • An identical publish keeps the agent’s ETag. An identical publish of a version published before 0.103.0 answers 409 version-digest-unknown, and writes nothing.
  • A create with If-None-Match: * of a resource that already exists answers 412 and writes nothing, for every resource that takes it, and for the agent’s first version. Two creates racing for one name or agent id, through the contention fixture: exactly one succeeds, and the other gets 412. Sending both headers is a 400.
  • Authorization before precondition, for publish, retire and restore. A caller without agent:publish on the agent’s current scope gets 404, both with a stale If-Match and with a current one, and nothing is written. A caller who holds the destination but not the current scope cannot move the agent. Sabotage: judge If-Match before the scope; the test must name the 412 it leaked. Then authorize outside the lock, with the agent moved between the check and the write by a test hook; the test must find the write made under the old scope’s authority.
  • A delete refused by an agent the caller cannot read answers 409 with hidden: 1 and no id. Sabotage: judge only the readable agents; the test must find the delete made.
  • Deleting an area that holds one row of each integration kind answers 409, once per kind, each with the kind named. A write into the area racing the delete, in both orders: either the delete answers 409 or the write is refused because the area is gone, never both succeeding.
  • The previous binary, against the delete. From the delete release’s side, the previous binary is the fence release. The test runs the fence release’s exact area-scoped settings upsert, lock included, for a connector instance and for a conversation, against a concurrent area delete held at its FOR UPDATE by a test hook. The upsert waits. Once the delete commits, it is refused because the area is gone, and no row exists at that area afterwards. Sabotage: drop the FOR SHARE from that upsert; the test must find a row written into the deleted area.
  • A write into an unregistered area is refused with 400 from the fence release on.
  • A classification at level: owner and one at level: platform for the same tool are two resources. Destroying the platform one makes the owner’s apply.
  • Retiring an agent writes a trail line.
  • Every secret field in api/openapi.yaml is writeOnly, found by walking the schema, so a new secret field without the mark fails the test.
  • An identical classification PUT writes no event and keeps the ETag.
  • An area PUT with an id folding would change answers 400.
  • For grants by a caller without identity:write, one test per rule, each using the input the broken version would accept:
    • a curator person granting curator, and a curator token granting curator;
    • a curator granting auditor;
    • a curator of area X granting in area Y;
    • a token granting approver;
    • a token granting to itself;
    • a token granting to another service account;
    • a token revoking an admin grant.
  • The grant GET answers 404 for a principal holding only the asserted twin of a grant, and 200 once the hand-set one exists.
  • A hand grant equal to an asserted one survives the identity provider withdrawing its assertion.
  • The email lookup answers one id or 404 for a caller with access:delegate, 403 without it, and never a list.
  • The lookup answers 429 past the caller’s limit.
  • A lookup that found nobody records found: false and nothing derived from the address: the row’s detail holds exactly the expected keys, and the address does not appear anywhere in the row.
  • A grant made by a token records that token’s id.

Provider side, in its repository, against a real server and database:

  • For every resource: create, read, update, import and delete.
  • An unchanged configuration plans empty right after apply and again later.
  • A change made through the API outside Terraform appears as drift on the next plan.
  • A test reads the state file after apply and finds no secret.
  • An apply against an autonomous agent is refused and changes nothing.
  • A plan putting an integration at area scope against a server older than its kind’s writers’ release fails at plan time and sends nothing.
  • Importing an integration by name fills scope, and the next plan is empty.

Decided

Section titled “Decided”

Decided by Kleber on 2026-11-11:

  1. Scope: three phases, as above.
  2. Access may be delegated, with identity:write still barred for tokens.
  3. Repository name: fuseone-io/terraform-provider-fuseoneagents.

Decided by the reviewer on 2026-11-11:

  1. Delegation by people: yes. One rule for people and service accounts, and the only role it grants is author.
  2. No force on delete. An emergency disables the resource and revokes or rotates its credential first, then edits or retires the agents, then deletes. The 409 never blocks disabling.
