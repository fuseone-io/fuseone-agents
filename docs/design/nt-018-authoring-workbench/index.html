NT-018 — The authoring workbench

Status: proposed · 2026-11-11 · revises NT-003 §4 · builds on NT-006, NT-015 and NT-016

What this is

Section titled “What this is”

Today an agent is authored in four separate places that do not talk to each other: an interview, a form editor, a batch simulation and an experiments page. Each works, and none of them feels like working on the agent. The author fills in a form, uploads a file of cases, waits for a report, opens a dialog to record a correction, and goes to another screen to compare versions.

This note specifies a single screen, the workbench, where the author:

  1. builds the agent by talking to an assistant, which proposes changes the author accepts one by one;
  2. rehearses it live on one case, answering for the world when the agent reads something and deciding as the approver when the Gate holds an action;
  3. corrects it in the same conversation, and the correction becomes both a draft change and a dataset case;
  4. experiments, running the draft against the dataset and comparing it with the version in production, without leaving the thread.

The interactive mockup the direction was chosen from is Bancada de agentes v2. It has a conversation on the left and a workspace on the right whose tab follows the mode: Rascunho, Ensaio, Experimento, Casos.

Who does what. An author holding agent:publish on the agent’s scope does everything on this screen, in the console. Nothing on it reaches a customer system, and nothing on it is done by an agent. Publishing remains a separate act by the same person.

Decided

Section titled “Decided”

Decided by Kleber on 2026-11-11:

  1. The conversation is free. The assistant chooses what to ask next. This revokes NT-003 §4 (“the interview is a wizard, not a chat”) and the comment at the top of internal/authoring/interview.go that rests on it. How the result stays reviewable is the subject of A free conversation, and what is reviewed instead.
  2. The author plays the world. In a rehearsal, nothing reaches a real system. When the agent calls a tool, the author types what the tool would have answered. The rule in internal/simulate/dry.go, that a simulated run has no way to reach a real system, stands unchanged.

Decided in review of e27dfcf7:

  1. Activation refuses a draft with no answer to “what must never happen”. An explicit “no restriction beyond the installation’s policies” counts. An empty block does not.
  2. One conversation per author over a shared draft. The draft, diff and trail are common, and ETag settles concurrency.
  3. SSE is deferred. Polling is the first version’s contract.

Decided in review of 39c96e0a:

  1. Policies are created only on the policies screen. For someone holding policy:write, the policy card opens that screen with the rule pre-filled. Review, simulation and saving stay behind its administrative boundary.

A free conversation, and what is reviewed instead

Section titled “A free conversation, and what is reviewed instead”

NT-003 kept the questions fixed because a creation path whose questions change every time cannot be reviewed, reproduced or audited. That argument is correct about the conversation. The answer here is that the conversation stops being the thing anyone reviews. Five rules replace the fixed questions.

1. The draft is the record, not the transcript

Section titled “1. The draft is the record, not the transcript”

The draft is a specification. It changes only by operations, and an operation lands only when a person accepts it. What is reviewed at publication is what is reviewed today: the specification, its narrative read-back, and now its diff against the version in production. Two conversations that reach the same draft produce the same agent, so reproducing the conversation does not matter.

2. The model proposes operations and never grants

Section titled “2. The model proposes operations and never grants”

Each assistant turn returns text plus zero or more proposals. A proposal is one typed operation:

Every operation edits a field AgentDefinition already has, and claims no more than that field does:

OperationEditsValidated against
add_tool, remove_tooltoolsThe catalogue, as read.go does today
set_block (add, replace or remove one block)instructions: objective, howToAct, whenToStop, neverLength limit
add_step, edit_step, remove_stepstepsreaches must be in the catalogue and in the draft’s tools
set_approval_deliveryapprovals (direct, notify)notify names people who may decide in the scope
set_triggertriggersThe same validation the form uses
set_model, set_budgetprovider, model, effort, budgetProvider registered; ceiling within the installation’s maximum

Scope, name and stage are not operations. The author sets them by hand. Scope decides who may act and stage decides how far the agent is trusted, so both stay human acts. A proposal that fails validation is shown crossed out with the reason, as the mockup does for pagamentos.estornar_cartao, and cannot be accepted. read.go grows from a filter on one reply into the validator of every operation.

No operation creates a Gate rule. approvals decides only where an approval is delivered (domain.ApprovalPolicy); whether a person must answer is decided by the installation’s policies, which need policy:write. The never block is an instruction the model reads, not a policy the Gate enforces. So when the author says “above R$ 500 the finance team approves”, the assistant does two things:

  • it proposes the never or howToAct text that tells the agent;
  • it shows a policy card, marked as not part of the draft. The card states the rule the author described, in the policy editor’s terms.

The card never says a current policy covers the request. The platform cannot prove that. POST /policies/simulate replays a new rule against past decisions; it does not test whether the installed rules imply the one asked for. It also needs policy:read, which an author holding only agent:publish may lack. A card reading “already covered” on that basis could lead someone to leave a needed approval with no rule. What the author can observe is the rehearsal. It runs under the installation’s policies as they are, so on that case the author sees whether the Gate held the action or let it through. The card says exactly that much: “the rehearsal will show what the current policies do on this case”.

What the card offers depends on who is looking:

  • Someone holding policy:write gets a link that opens the policies screen with the rule pre-filled. Review, simulation and saving stay on that screen, behind its own administrative boundary.
  • Anyone else is told to ask a policy administrator. The card never names who holds policy:write. Finding that out means reading the directory and the grants, which is administrative and reveals identities, and no API grants it to an author.

An author’s acceptance never becomes policy:write.

3. The seven questions become a checklist

Section titled “3. The seven questions become a checklist”

The PRD §6.1 schema is still the schema. The checklist shows which of its seven parts the draft covers:

  • trigger;
  • read tools;
  • steps;
  • exceptions per step;
  • approval points;
  • closing criterion;
  • what must never happen.

The checklist is computed from the draft, not from the conversation, so it is deterministic. The assistant is told which parts are missing and asks about them in whatever order the conversation allows. This keeps the PRD’s best idea, “what must never happen?”, without making it question seven of a form. PRD §6.1 is amended in the same change: from “not a free-form prompt” to “a conversation that fills a fixed schema, which the platform checks”.

Activating a candidate refuses a draft without an answer to “what must never happen”. An explicit answer of “no restriction beyond the installation’s policies” counts, recorded as such in the never block. An empty block does not count: an empty block is not a decision. The other six parts are shown, and do not block.

4. Acceptance leaves a trail; the transcript is content

Section titled “4. Acceptance leaves a trail; the transcript is content”

Every accepted operation is a row in the authoring trail:

  • draft;
  • operation kind;
  • digest of the operation;
  • the turn it came from;
  • who accepted it;
  • when.

Following the rule that immutable rows hold no free text, the row carries ids and digests only. The operation’s body and the transcript live in the content store under owner kind authoring, under the installation’s retention.

Each author has their own conversation over the shared draft. The draft, its diff and the trail of accepted operations are common; the threads are not. That keeps one author’s pasted tickets out of another’s context.

Where text ends up, and how erasure follows it

Section titled “Where text ends up, and how erasure follows it”

A sentence typed in a turn can be copied to four places:

  • the transcript;
  • the body of the operation proposed from it;
  • the draft value that operation wrote;
  • the content of every candidate sealed while that value stood.

Erasure has to reach all four, so provenance is kept on the values, not just on the conversation.

  • Each draft value carries its provenance: the ids of the operations that wrote its current text, and through them the turns and any run those turns referenced. A value the author typed by hand carries the author’s id instead.
  • Each seal records the provenance of every value it sealed.

Erasing a thread, or erasing a run a turn referenced, clears four things in one transaction:

  1. the transcript turns involved;
  2. their operation bodies;
  3. every draft value whose current provenance includes one of those operations. The value is replaced by an erasure marker, the draft’s ETag moves, and the checklist shows the part as missing;
  4. the content of every unpublished seal that sealed such a value. That candidate becomes impossible to activate (see Retention).

A value later overwritten by hand no longer carries the erased operation, so it stays.

Subject erasure is promised only where the platform can know the subject:

  • Content brought in by reference. When the author starts a rehearsal from a run, or imports a case, the turn records that run’s id. Subject erasure of that run follows the reference along the chain above, as NT-015 makes it follow the corpus copy.
  • Anything typed or pasted. A partial paste has no digest in common with any run, so subject erasure cannot find it. It is covered by retention, and by erasing the thread. The thread’s author, or anyone with data:erase on the scope, can erase it, and that follows the same chain. The screen says this at the composer, so the author is not left assuming a promise the platform cannot keep.

Only the published row is out of reach. Activation writes the sealed bytes into agent_specs, and that row is never erased, because runs are pinned to it (spec/retire.go). Everything else stays erasable after activation, along the same chain:

  • the transcript;
  • the operation bodies;
  • the draft’s values;
  • the seal’s own copy in the content store.

The activation screen shows the full text going live and says that this text is kept. That is the last point where the author can remove what should not stay.

5. What the author pastes is untrusted

Section titled “5. What the author pastes is untrusted”

A pasted ticket can carry instructions. The model reads it as data, but the real protection is rule 2: nothing reaches the draft without a person accepting a typed, validated operation. Proposals made in a turn whose context includes pasted content are marked as such on their card, so the author knows where a suggestion came from.

Cost

Section titled “Cost”

Each turn is an authoring call and counts against the existing daily ceiling. ErrOverCeiling ends the conversation for the day and leaves the draft intact. The form editor still works. NT-003 §5’s requirement that an installation with no authoring provider can still publish agents is kept: without a provider the workbench opens with the conversation disabled, and the draft is edited by hand.

The draft lives on the server

Section titled “The draft lives on the server”

A conversation that proposes operations needs something to apply them to that survives a reload and that a second tab can see. Today the draft is in sessionStorage.

  • A draft is mutable working state, not the ledger and not a version. It lives in a table of its own, holding the specification, the version it started from, and an ETag.
  • One draft per agent, shared by its authors. Applying an operation takes If-Match and answers 412 when the draft moved. The same pattern is used for the API in NT-017.
  • The draft’s values carry provenance, and erasure clears them along the chain in where text ends up.

Candidate versions

Section titled “Candidate versions”

A rehearsal and an experiment have to run a specification that cannot change under them. A draft can change. Publishing makes a version current (publisher.go:102), which would put an untested draft into production.

So the workbench seals a candidate: a version digest that is not current and has never been published. The digest is computed exactly as publication computes version_id, so a candidate that goes live keeps its id. Sealing and activating are two acts, with different checks.

How a candidate is stored

Section titled “How a candidate is stored”

agent_specs is not touched. It stays insert-only (0006_agent_specs.sql), and a row there still means “published”. Candidates live in a table of their own, agent_seals, which is also insert-only.

A seal keeps the whole definition, as bytes. version_id is the digest of the specification file’s bytes (versionOf, spec.go:286). The only copy that cannot drift from the digest is therefore those exact bytes. They carry every field the definition has: name, company and area, provider, model, effort, fallback, cache TTL, reply locale, tools, budget, triggers, steps, emits, memory learning, approvals and instructions. The bytes go to the content store under owner kind authoring and owner seal_id. p.judge, the rehearsal, the experiment and activation all parse those bytes, never a reconstruction.

Each row of agent_seals is one act of sealing, and holds only indexable metadata and the reference:

  • (agent_id, version_id, seal_id);
  • the sealed scope, company and area as they stood in the bytes;
  • who sealed it, and when;
  • the reference to the bytes;
  • the provenance of the draft values it sealed.

A candidate is a version_id with at least one seal and no row in agent_specs. Because one version can have many seals, the cases that collide today resolve without any update:

CaseResult
The draft’s digest is already publishedNo seal is written. The workbench rehearses, experiments on and activates that published version. Activation takes the already-published path of step 10.
Two authors seal the same digestTwo seals, one candidate. The trail records both.
An ordinary publication of the same digest while a candidate existsagent_specs gains the row, and from then on the version is published. Its seals stay as history. Activation takes the already-published path of step 10, even if every seal has since expired.
The candidate’s text aged out or was erasedRe-sealing from the draft writes a new seal, with a new content reference. Nothing is restored over a tombstone.

That last row matters. Content.RestoreFor clears any tombstone, including one left by subject erasure. A candidate that restored its text by digest could bring back what an erasure removed. A seal never restores. Text erased from the draft also gives a different digest when re-sealed, so it cannot come back that way either.

Who can see and use a candidate

Section titled “Who can see and use a candidate”

Every door authorizes against the sealed scope, never the agent’s current scope. This covers listing, reading, rehearsing, experimenting and activating. Each of them needs agent:publish on the sealed scope. A candidate is unpublished work, so agent:read is not enough to see it. Outside that scope the answer is 404, as for a version that does not exist.

So when an agent moves from finance to cx, an author in cx gains nothing sealed in finance. Activation also needs the agent’s current scope, and the order of the checks is what keeps the move from leaking. These are steps 2, 6, 7 and 8 of activation. The current scope is read under the agent’s lock, and no precondition is judged before it:

  1. agent:publish on the sealed scope, or 404;
  2. read the agent’s current scope;
  3. agent:publish on the current scope, or 404. A finance author must not learn that the agent now lives in cx, so an author who cannot act there gets the same answer as for a candidate that does not exist. This includes the 412 a stale If-Match would give, which is judged only after this check;
  4. only a caller who can act in both scopes, and finds them different, gets 409 fuseone:candidate-scope-moved. Publishing those bytes would move the agent back without anyone deciding to. The way forward is to re-seal from the draft in the new scope.

A first version has no current scope, so check 3 uses the sealed scope again (see the first version).

Sealing

Section titled “Sealing”

Sealing checks that the author holds agent:publish on the scope, and runs p.judge so the rehearsal shows the same graph findings a publication would. It takes no lock: its judgment is informational, and activation judges again under the lock. It does not run refuseStage. Rehearsing an improvement to an autonomous agent is safe; putting it live is what must be refused.

A candidate never opens a real run

Section titled “A candidate never opens a real run”

A candidate has no row in agent_specs, so it is invisible by construction to three places:

  • the current-version fallback (catalogue.go:41, event_graph.go:79, standing/create.go:39);
  • Registry.Versions;
  • trigger.Pin (trigger/version.go:15).

A real run, a rerun included, can only pin a version Pin finds. A rehearsal or experiment request resolves a candidate through a separate lookup on agent_seals. The Opener (trigger/open.go:187) accepts that lookup only for a simulated run marked as a rehearsal or an experiment. Any other request naming a candidate gets the same error as a version the agent never published, so a candidate’s id reveals nothing. The tests below hold this fence even though the table split already enforces it, so that a later change merging the lists breaks a test, not production.

Activating

Section titled “Activating”

Publishing from the workbench activates the candidate that was experimented on. It does not seal a fresh one, so the digest that went through the experiment is the digest that goes live. Activation repeats every guarantee of a publication, in one transaction.

Activation checks the same things a publication does, plus the candidate’s own conditions. The order below is the order the code runs, so no answer can reveal more than the caller is entitled to see, and nothing judged under a lock was read before it.

Before any lock. Nothing here reads the agent.

  1. Headers, by syntax only. Exactly one of If-Match and If-None-Match: * must be present, or the answer is 428. A value that does not parse is 400. Neither header is judged yet.
  2. The version’s scope. Look the version up in agent_specs first, then in agent_seals. Take the scope from whichever row is found: the published version’s company and area, or the seal’s. Check agent:publish on that scope. If neither row exists, or the caller lacks the permission, the answer is 404. A caller who passes this step has been allowed to know the version exists. If the version is in both tables, the caller must hold agent:publish on both rows’ scopes, or the answer is 404. Which row defines the version is decided only in step 10, by full digest.

Under the locks, acquired in the one order every writer uses:

  1. The agent’s content fence, shared (Hold), once for the whole request. See the fence below.
  2. The event graph lock (lockEventGraph, publisher.go:71).
  3. The agent’s agent_state row, FOR UPDATE. A first version may have no row; the event graph lock already serializes it (see the first version).
  4. The current scope. Read it now, under the lock, and check agent:publish on it. If the caller lacks the permission, the answer is 404. For a first version, the scope is the sealed one. Because this read happens under the lock, the scope cannot move between this check and the decision.
  5. The precondition. Judge If-Match against the agent’s ETag as NT-017 defines it (in review, #321): one tag covering the current version and whether the agent is retired. It is the same tag publication and retirement honour, not a weaker one derived here. Retiring or restoring the agent during the experiment therefore stales the tag, as publishing does. If-None-Match: * is judged against whether any version exists. A mismatch answers 412 with the current ETag. Only a caller who passed step 6 can receive this, so a 412 never tells an outsider that the agent exists or changed.
  6. The scope move. If the sealed scope differs from the current one, the answer is 409 fuseone:candidate-scope-moved.
  7. The stage. refuseStage with autonomous, on the row already locked.
  8. The definition. Still under the event graph lock, which no publication can pass, decide which row defines the version and load it in full. Every later step judges this definition and nothing else. Read the version’s claim first (see the full digest). A NULL claim answers 409 fuseone:version-digest-unknown.
    • Already published. agent_specs has the version. The claim proves its bytes are the bytes every seal of this version_id sealed. The definition is the published row. No seal is read, and none has to be readable, so an expired or erased seal does not block activating a version that is already published.
    • Still a candidate. Only agent_seals has the version. Read a seal’s bytes. If no seal is readable, the answer is 409 fuseone:candidate-unreadable. Check that the full SHA-256 of the bytes equals the claim, then parse them. The parsed definition is the candidate.
    • A seal whose bytes do not match the claim. The answer is 409 fuseone:version-collision, and nothing is written. Claims make this unreachable through any writer; the check is there for a row written around them.
  9. The named resources, FOR SHARE, in ascending order of id, as the definition from step 10 names them. Each one must still exist: tools, provider, connector instances, area. This is the fence NT-017 specifies for publishing (in review, #321).

With nothing left to acquire:

  1. The graph. p.judge on the definition from step 10, against the graph as it is now, its emits included.
  2. The checklist. The definition’s never block must be answered (see the checklist).
  3. The write. On the published path, make the row current. On the candidate path, insert the agent_specs row from the bytes and make it current. The claim already exists, because the seal wrote it. Record the activation’s provenance either way.

The full digest

Section titled “The full digest”

version_id is not proof that two definitions are the same. It holds 12 hex digits of the SHA-256 (spec.go:286), which is 48 bits. Which definition goes live, under which scope, and whether it is the one an experiment ran, all hang on that identity. So every writer compares the full SHA-256 of the original bytes, and the comparison is atomic across writers.

One claim per identity

Section titled “One claim per identity”

A new insert-only table, agent_version_digests, maps (agent_id, version_id) to the full digest, keyed on that pair. It is the only record of which bytes a version_id names. Every writer that creates an identity claims it first, in its own transaction, before judging anything:

  • Publisher.Publish: console, API and Terraform;
  • Registry.Publish, which the disk sync calls directly (cmd/agentd/sync.go);
  • sealing.

A claim is insert … on conflict do nothing, followed by reading the row back. Before claiming, a writer of a version checks whether agent_specs already has the pair. If it has, and there is no claim, the writer refuses with fuseone:version-digest-unknown and never adopts the digest it was given. That row was written by a binary that kept no digest, so claiming the new bytes would record, permanently, that the old row holds them. The writer leaves the pair unclaimed, and C2’s migration claims it NULL. The check is race-free: every writer of agent_specs, the previous binary’s included (Publisher.Publish, Registry.Publish, MakeCurrent), runs under the event graph lock, and so does the check.

  • If the row holds the same digest, the claim stands and the writer continues.
  • If it holds a different one, the answer is 409 fuseone:version-collision, before any judgment and before any other write.

The primary key is what makes this atomic. Two transactions claiming the same pair with different digests cannot both succeed: the second waits on the first’s uncommitted row, then either finds the committed digest, or finds no row if the first rolled back, and inserts its own. There is no window where a seal A and a publication B both see “no conflict”. The claim is written in the same transaction as the version or the seal, so a rolled-back publication leaves no claim behind.

The claim adds no lock cycle. Publication takes it after the event graph lock, and sealing takes no other lock. Activation reads the claim in step 10, which the seal already wrote.

So the precedence in step 10 only ever chooses between rows that share one digest. A collision is refused where it would have been created, not discovered at activation after B is already live.

Versions published before the table

Section titled “Versions published before the table”

A migration inserts a claim for every existing row of agent_specs with digest NULL, because its original bytes were never kept and serializing the row would not recover them. A claim whose digest is NULL cannot be matched by anything.

Decided by Kleber on 2026-11-11: a publication or a seal whose version_id lands on a NULL claim is refused with 409 fuseone:version-digest-unknown. The way forward is to change the definition. A change almost always gives another id. Because the id is 48 bits, it may instead land on another claim, and that too is refused, never resolved silently. The author then changes the definition again.

This is a change in behaviour. Today, republishing identical bytes of an old version makes it current again (publishOn is on conflict do nothing, registry.go:130, followed by makeCurrentOn). For versions published before the table, that stops working. It cannot stay: p.judge would judge the definition being published, the insert would keep the old row, and MakeCurrent would activate a definition nobody judged.

The disk sync republishes every version on disk at each boot. A version whose claim is NULL is refused there too. The sync reports it and skips it (a log line naming agent and version, and a counter) instead of failing the boot. The version stays in agent_specs as it was, and stays current if it is. Rewriting the file, which gives a new id, is how it gets a digest.

The database enforces it, against the previous binary too

Section titled “The database enforces it, against the previous binary too”

A rule kept only in the new binary is not yet a guarantee. Migrations run as a pre-upgrade hook (deploy/helm/fuseone-agents/templates/migrate-job.yaml), and the previous release’s serve replicas keep answering through the rolling update. Those binaries insert into agent_specs and call makeCurrentOn knowing nothing of claims (publisher.go:99). Left unchecked, they could:

  • publish a new version with no claim;
  • make a legacy version with a NULL claim current again;
  • do either again after a rollback to that release.

So the claim is enforced in the database, by two triggers. They are installed only once every replica writes claims, which takes two releases.

Release C1, the claimers. Its migration does three things:

  • it creates agent_version_digests;
  • it adds the nullable agent_specs.digest column;
  • it inserts NULL claims for every row of agent_specs.

Its binary claims on every write, in all three writers, fills the column, and refuses a row that exists without a claim, as above. It installs no trigger. While C1 rolls out, a C0 replica can still write an unclaimed row or make a NULL version current. That is exactly today’s behaviour. C1 does not legitimize those rows: it refuses to claim them. The window ends when C1 runs on every replica, and nothing in the workbench exists yet to collide with.

Release C2, the enforcers, ships only after C1 is deployed on every replica. Its migration does three things, in one transaction:

  1. It claims the gap. Every agent_specs row still without a claim gets a NULL one. Those rows are C0 writes from C1’s rollout, and their bytes were never kept.

  2. It refuses any insert that does not present a matching digest. A trigger BEFORE INSERT on agent_specs requires two things:

    • NEW.digest is not NULL;
    • there is a claim for (agent_id, version_id) whose digest equals NEW.digest.

    A C0 insert never sets the column, so it is refused whether or not the id is already claimed. That closes C0 publishing a colliding B over a claimed A. A BEFORE INSERT row trigger fires before on conflict do nothing checks for the conflict. So the insert C0 believes is a harmless no-op is refused, and the transaction that would have gone on to makeCurrentOn aborts with it.

  3. It refuses an unproven current version. A trigger BEFORE INSERT OR UPDATE OF current_version on agent_state refuses a current_version whose claim is missing or NULL. It has two guards, and it raises only when both pass:

    • NEW.current_version IS NOT NULL. Six statements create or touch an agent’s state before it has a version, and all of them must keep working:
      • refuseStage’s ensure state (publisher.go:142);
      • SetStage, SetPaused and EnsurePaused (state.go:95, :126, :144);
      • retirement (retire.go:30).
    • On update, the value changes (NEW.current_version IS DISTINCT FROM OLD.current_version). The disk sync’s MakeCurrent of the version that is already current therefore still passes, and so does every legacy version that is current today.

Because C2’s migration runs while C1 replicas serve, and C1 presents its digests, the triggers refuse nothing C1 does legitimately. They refuse every agent_specs insert C0 can make, and every C0 move of the current version to a version without a proven digest.

Rollback floor. Once C2’s migration has run, rolling back below C1 is not supported. Every C0 publication would be refused by the trigger. That fails closed, with no wrong row written, but publishing stops until C1 is back. Rolling back from C2 to C1 is safe, because C1 claims. The release notes of C2 state the floor.

The workbench writes seals only after C2. The collision guarantee rests on the triggers, so phase 2 ships in C2 or later.

The digest travels from the bytes, never from a Spec

Section titled “The digest travels from the bytes, never from a Spec”

Parse computes the SHA-256 and keeps only 48 bits of it in Spec.Version (spec.go:165). The HTTP route renders the definition to bytes and parses them (httpapi/publish.go:339). The disk store parses each file (spec/store.go:143). Both then hand on only the Spec. Re-serializing a Spec does not recover the bytes, so the full digest has to be carried, not recomputed:

  • Spec gains Digest, the full hex SHA-256 of the bytes Parse was given. Only Parse sets it.
  • Publication carries the Spec and with it the Digest. So do Store.Get and the seal path.
  • Registry.Publish and publishOn refuse a Spec whose Digest is empty, or does not begin with the hex in Version. A Spec built by hand or reconstructed from a row cannot publish. It fails closed instead of claiming a digest of bytes that never existed.
  • agent_specs gains a digest column, which the writer fills from Spec.Digest on insert. It is not a second record: the claim is the record, and C2’s trigger requires the column to equal the claim. The column is how an insert presents its digest to the database, which is what lets the database tell a writer that knows the bytes from one that does not.

Lock order

Section titled “Lock order”

The lock order is the publication’s, and it is the only one. Steps 4, 5 and 11 are the order Publisher.Publish uses today (event graph, then the agent row inside refuseStage). Ordinary publication adopts the resource tier when NT-017’s fence lands, so activation and publication can never wait on each other in a cycle.

The content fence (step 3) comes before every database lock. It is the fence an erasure and anything copying an agent’s content already share (regression/fence.go, domain.CorpusFence). Each acquisition opens its own connection (fence.go:53), so a request that entered it twice would wait on itself. A request enters the fence exactly once, from the outside:

  • Experiment opening already runs inside regressions.Exclusive (openExperiment, httpapi/experiments.go:79). It resolves the candidate inside that acquisition and takes no second fence.
  • Rehearsal opening and activation take it shared, with Hold, around their whole transaction.

Every erasure that can reach a seal holds the fence exclusively: by thread, by referenced run, by subject, and by retention. An erasure takes only the fence and content rows, so it never waits on the event graph or an agent row. That leaves two possible orders, and both are safe:

  • activation first: the erasure waits, then erases the seal’s copy. The published row is the one copy erasure never reaches, and the screen said so;
  • erasure first: step 10 reads a tombstone and fails closed.

If any step fails, nothing changes, and the candidate stays a candidate.

The first version of an agent

Section titled “The first version of an agent”

An agent the workbench creates has no published version, so there is no current version to match and no current scope. If-Match refuses any value on a resource that does not exist (openapi.yaml, IfMatch), so a first activation cannot use it. It uses the opposite precondition instead:

  • If-None-Match: * means “this agent has no published version”. It is judged under the event graph lock as a read of agent_specs for the agent. If any version exists, the answer is 412 and nothing is written.
  • The scope comes from the seal. It is authorized as the sealed scope, twice: step 6 of activation has no other scope to read.
  • The agent is born paused, in stage draft. makeCurrentOn already creates the agent_state row paused when the agent has none, and a missing stage reads as draft. So a first activation, like a first publication, starts nothing.

Serialization does not depend on an agent_state row existing. FOR UPDATE on a row that is not there locks nothing. But the event graph lock is a single installation-wide advisory lock (event_graph_lock.go:30), taken first by Publish and by activation alike. A first activation and an ordinary first publication of the same agent therefore run one after the other:

  • publication first: the activation’s If-None-Match: * finds a version and answers 412;
  • activation first: the publication sees a published agent, and proceeds as any publication over an existing version does.

Reading a candidate during a run

Section titled “Reading a candidate during a run”

The fence guards opening a run. The worker reads the specification again on every turn (worker/turn.go:51 calls resolve), in another process and long after the opening request returned. Holding the fence across a turn would hold it across a model call. Erasure would then wait on the model, and a fence slot (FenceSlots is 4) would be held for as long as the model takes.

A turn does not need the fence, because it reads and does not copy. The bytes go into the prompt, and nothing durable is written from them except what the run records as its own content. A single read sees either the bytes or the tombstone, so the linearization point is that read. The promise is stated exactly:

  • a turn whose read happens after the erasure commits finds the tombstone, ends with a failed step carrying fuseone:candidate-unreadable, and plans nothing;
  • a turn whose read came first may finish its one model call with the old text. No later turn of that run, or of any other run, reads it.

So erasure of a candidate takes effect at the next turn of a run already open, never mid-turn.

Every run records where its text came from

Section titled “Every run records where its text came from”

What the model writes back can repeat the candidate’s text, and that output is the run’s own content. Rehearsals are not the only runs that read a candidate: an experiment started in the thread runs the same seal over thirty cases. So every run that reads a candidate records its origin when it opens, in rehearsals and experiments alike:

  • the seal_id it read;
  • the thread it was started from, if any.

The origin goes in run_started, and nowhere else first. The index an erasure reads is a projection of that step, written in the same transaction. upsertRun (ledger/append.go:207) already projects runs from each step inside the append transaction, and reads simulated and simulation from the run_started payload. It gains seal_id and authoring_thread the same way, as two id columns on runs with an index each. A run that exists therefore always carries its origin: there is no second write that can fail on its own. The contract suite that checks the projection against a Go fold covers the two new columns.

An experiment fixes its seal in the intention, not per run. An experiment opens its runs under an idempotency key, and a retry reads what the first attempt recorded (openExperiment, simulate.Recorded). The seal and the thread join the recorded intention:

  • the first run the experiment opens fixes seal_id and thread;
  • a retry that omits them inherits the recorded ones;
  • a retry that names a different seal is the existing conflict, “a retry stating another intention than its key’s”;
  • the seal follows the idempotency contract of #309, as the provider and the corpus already do (openExperiment, “refused only before anything was opened”):
    • a first attempt that has opened nothing, and finds its seal unreadable, is refused with fuseone:candidate-unreadable;
    • a retry of an experiment that already has runs is never refused for something that changed underneath. If seal A is unreadable, the retry opens zero new runs and answers from the ledger (answerFromRecord), as it does when the corpus was erased. It never opens the missing runs on sibling seal B, even though B’s bytes are the same. Every run of one experiment read the same seal, so one erasure reaches all of them.

A run is pinned to the seal it opened with. Every turn resolves that seal, never another seal of the same version. If that seal is unreadable, the turn fails closed even when a sibling seal is readable. That keeps the origin exact: the run read one seal’s bytes, and erasing them reaches it.

Erasure then follows the origin. Erasing a thread, or erasing any seal along the chain in where text ends up, also erases the content of every run whose origin names that thread or that seal. That covers rehearsals and experiments, including an experiment started from the experiments page on a candidate sealed from the thread. The erasure is by owner (EraseOwnersTx with run), in the same transaction and under the same exclusive fence. Text the model echoed back goes with the run.

Retention

Section titled “Retention”

A seal’s text lives in the content store under the installation’s retention, counted from the seal. When it is gone, through age or erasure, the platform fails closed:

  • Activation with no readable seal for the version answers 409 fuseone:candidate-unreadable. It never publishes partial text, and never publishes text that does not match version_id.
  • Opening a rehearsal or experiment run on such a candidate is refused with the same code, before any run exists.
  • A run already open that cannot read its candidate’s text at its next turn ends with a failed step carrying that code, as reading a candidate during a run states. It never continues on a partial specification. An experiment counts that case as not_comparable.

The way back is to re-seal from the draft. If the text is unchanged, the new seal has the same version_id, so the experiment evidence still applies to the same digest. If erasure changed the text, the new seal has a different digest and needs its own experiment.

Live rehearsal

Section titled “Live rehearsal”

A rehearsal is a simulated run of a candidate on one case the author typed or pasted. It uses the same Gate, ledger and budget as today’s simulations.

A rehearsal is not a battery

Section titled “A rehearsal is not a battery”

Today a run that is simulated, names a simulation and a case, and names no experiment counts as evidence about the agent. A rehearsal would match that description:

  • HasSimulation (ledger/simulations_postgres.go:45) would let one rehearsal take the agent out of Draft;
  • Batteries and LastBatteryAt would let it reset the clock the drift sweep reads.

So run_started gains rehearsal, and the three readers exclude it, in Postgres and in ledger.Memory. An older replica would still count a rehearsal, so this ships the way experiments and judges did: the readers in one release, deployed on every replica, before the release that first writes a rehearsal.

The endpoints that answer for the world and decide in a rehearsal accept only a run marked rehearsal, stopped at exactly the request being answered (atSeq, as DecideApproval requires today). A real run, a battery or an experiment is refused.

Two things are new in the run itself.

The author answers for the world

Section titled “The author answers for the world”

In rehearsal, simulate.Deps swaps in a tool layer whose Invoke parks the run, instead of DryTools, which returns empty at once. The run waits for an answer the way it waits for an approval:

  • the call is recorded as today;
  • a world_awaited step marks the wait;
  • the author’s answer is stored in the content store, and a world_supplied step records its reference and digest.

The answer carries LabelUntrusted, because it is external content as far as the agent’s next decision is concerned. Calling it trusted would let a rehearsal take a path production would refuse.

Deps remains the only constructor. The parking layer, like DryTools, has no argument or flag by which it can reach a real system. The test that guards dry.go today is extended to cover it.

Writes are answered by the author too, for example a refund id. Nothing executes, and the Gate has already decided whether the call was allowed before the author is asked.

The author decides as the approver

Section titled “The author decides as the approver”

When the Gate holds an action, the rehearsal shows the decision in the trace. The author’s decision is recorded as a rehearsal_decided step. It is never approval_decided, so no count, report or audit of real approvals can mistake it for one. It needs agent:publish on the scope, not approval:act, because it authorises nothing.

Before this ships, one existing door must close. DecideApproval (internal/httpapi/approvals.go:80) does not check whether the run is simulated. Simulated runs are hidden from the inbox, but a direct call by someone holding approval:act would record a real approval_decided on a simulated run. We have not verified whether the simulation pool resumes the run afterwards. Either way the record is wrong, so DecideApproval refuses simulated runs, tested with a simulated run held at awaiting_approval.

Watching it happen

Section titled “Watching it happen”

There is no streaming today. Polling is the contract of the first version: every second while a rehearsal is active and the run is not waiting on the author. A rehearsal spends most of its time waiting for the author, so polling at that rate is cheap. SSE is deferred. It is reopened only after phase 4 has been measured in use and under load.

Correction becomes a case

Section titled “Correction becomes a case”

POST /agents/{id}/regressions already accepts a simulated run. The workbench calls it with the rehearsal’s run when the author accepts a correction. One accepted correction produces two things: an operation on the draft and a case.

The new part is that a case keeps the world. The answers the author typed in the rehearsal are copied into the case, by reference and digest, beside the input. Without them, replaying the case in an experiment would go back to empty tool results, and the case would test a different situation from the one the author corrected.

The recording is a sequence. Each entry holds:

  • its position;
  • the tool;
  • a digest of the arguments;
  • the reference to the answer.

The same call made twice with different answers is two entries, not one ambiguous key.

In an experiment, a case with a recording runs on a replay layer that answers calls strictly in order. Each entry is consumed once. The case is marked not_comparable, with the first divergence named, when a call is:

  • missing: the run settles before the recording is consumed;
  • extra: a call made after the recording is exhausted;
  • repeated: an entry asked for a second time;
  • out of order: a call matching a later entry rather than the next one.

From that point the run gets empty results. This uses the comparison’s existing state, so a case that behaves differently from the recording is never reported as held. Matching strictly in order is deliberate. It will mark as not_comparable some runs that reorder two independent reads, which NT-003 §8 allows inside a step. That costs a re-recorded case. The alternative is a replay that picks an answer for the agent, and that would be the platform inventing evidence.

NT-015’s erasure rules apply to the recorded answers as they do to the input, since both came from the same rehearsal:

  • erasure follows the input;
  • erasure and copying exclude each other;
  • deleting a case erases its copies.

Each new case creates a new dataset version, as NT-015 specifies.

Experiments in the thread

Section titled “Experiments in the thread”

No new mechanism. “Rodar contra os casos” starts an NT-015 experiment that pins three things:

  • the candidate;
  • the latest dataset version;
  • the candidate’s configuration.

The thread then shows the comparison against the current version. Each case’s was/now maps onto the mockup’s three colours:

  • held to held: kept;
  • broke to held: fixed in this version;
  • held to broke: a regression.

The regressions are listed with a link that opens their trace in the Ensaio tab. Judge opinions appear beside the verdict once NT-016 release 2 opens judge runs. Until then, the column is absent rather than empty.

What this is not

Section titled “What this is not”
  • Not a way to reach production data. Reads in a rehearsal are answered by the author. NT-003 §10’s rule that authoring does not touch customer data stands.
  • Not a model that publishes, grants or promotes. It proposes typed operations. A person accepts each one, publishes, and promotes the stage.
  • Not a replacement for the form editor or the API. Both stay, and NT-017’s Terraform provider publishes versions without passing through here.

Tests that must exist

Section titled “Tests that must exist”

Each is written red first. Each sabotage uses the value the bug would accept.

  • An operation naming a tool outside the catalogue is refused. Sabotage: drop the catalogue check in the validator; the test must name the tool.

  • No operation changes scope, name or stage. Sabotage: accept a set_scope op.

  • Applying an operation with a stale ETag answers 412, and the draft is unchanged.

  • A trail row holds no free text. A CHECK or a test reads every column against a pasted string.

  • A rehearsal run cannot reach a real tool. Extend dry.go’s guard to the parking layer.

  • rehearsal_decided never counts as an approval. Use the approvals listing and the stats against a run that has one.

  • No operation writes a policy. The sabotage is an operation that takes an author holding only agent:publish to a stored policy; the test must name the operation.

  • A rehearsal naming a candidate is accepted, and so is an experiment.

  • A first activation and an ordinary first publication of the same agent, run concurrently in both orders, give the two results listed in the first version. Neither leaves two current versions.

  • The scope checks run in their stated order. After a move from finance to cx:

    • an author who can publish in both scopes gets 409 fuseone:candidate-scope-moved.

    Sabotage: check the scope move before step 3; the test must name the leaked 409.

One experiment is started from the thread and one from the experiments page. After the thread is erased, the string is found in neither kind of run. Sabotage: erase only rehearsal runs; the test must name the experiment run where the string survived.

If A is erased before the retry, the retry answers 202 from the ledger, as POST /experiments always does, opens zero runs, and opens nothing on B. A first attempt with no runs and an unreadable seal is refused.

Sabotage: check for a conflict with a select instead of claiming; the test must find two digests live.
