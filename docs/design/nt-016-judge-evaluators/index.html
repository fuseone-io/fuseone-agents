NT-016 — Judge evaluators

Status: proposed · 2026-11-10 · extends NT-006 and NT-015 · issue #298, phase 3 of #261

What this is

Section titled “What this is”

An experiment answers did this configuration break what we already corrected? Every expectation it checks is structural and binary: which tool was reached, whether the run asked, what it cost. It cannot answer is the answer any good?, because that question is about text, and only a model reads text.

This note specifies a judge: a rubric, run by a model, over the outputs of an experiment that has already settled. Its result is an opinion with a provenance. It sits beside the structural verdict and never changes it.

Who does what. An author with agent:publish on the scope where the experiment was recorded asks for a judgment of that experiment, in the console or through the API, and sees what it may cost before it starts. Reading one needs agent:read on that scope, as reading the experiment does. Nothing here is done by an agent, and nothing runs unattended: online evaluation is phase 4, and it needs its own decision.

What is already decided

Section titled “What is already decided”

From NT-006 §5, NT-015 and #298:

  • Provenance. A judged result is an opinion: rubric digest, model and cost, recorded apart from the Gate’s verdicts.
  • No effect on structure. It never enters the held and broken counts, so a structural breach fails the case whatever its score.
  • Untrusted output. #298 asks that a run must not be able to talk its way to a high score, shown by a hostile test. This note narrows that requirement, because no mechanism can meet it as written (see Untrusted output). The platform guarantees structural isolation. It measures how well a judge resists persuasion, and it does not promise that it does.
  • Same execution path. Judges run through the model registry, and their cost is in the ledger.
  • No schema change. Results attach to a run and a case.
  • No ensemble. NT-006 §5 leaves it out: it multiplies cost for the less important column.

A judgment is a set of runs

Section titled “A judgment is a set of runs”

Three ways to run a judge were considered.

OptionWhy not
A call outside any run, the way the authoring assistant uses model.CompleterCompleter exists because the assistant spends outside a run, and its cost comes back with the answer and goes nowhere. A judge would be the same: no ledger, no ceiling, no trail.
A step appended to the judged run, after run_finishedIt gives the run a second writer once its owner is done (NF-15), and the experiment’s cost per run would start including the judge’s.
A run of its ownIt gets the worker pool, the lease, the per-run ceiling, the ledger and erasure without anything new.

So a judgment is one rubric, one judge configuration and a number of repetitions, applied to one settled experiment. Each judged output gets one judge run per repetition. A judge run:

  • is simulated, under the judged run’s agent and version and the scope the experiment was recorded in, not the scope the agent is published in today;
  • records on run_started the same experiment id as the runs it judges, the judged run’s case, the judgment’s id as its simulation (see One judgment per key), and a judge field: the judged run, the rubric digest and reference, the judge configuration, the per-run ceiling, the repetitions asked for and this run’s repetition;
  • is opened with the case’s input as its input, held as its own content, as a battery run’s is, plus a copy of the judged run’s output, whose digest equals that run’s OutcomeDigest;
  • is offered no tools: its pack is empty, whatever the judged agent declares. It runs in the simulation pool anyway, where simulate.Deps puts DryTools in place of the tool layer, and it gets no memory and no context artifacts.

Carrying the experiment id is what keeps the gate safe on binaries that know nothing of judges. HasSimulation, Batteries and LastBatteryAt exclude every run that names an experiment, and every replica has done so since 0.100.0. A judge run therefore cannot let an agent leave Draft, start or stop a version, or reset the battery clock, even on a binary that was never told about it.

Its own simulation id is what keeps the experiment’s own record intact. simulate.Recorded, Gather and the experiment report read the runs under the experiment’s simulation id, so a judge run is in none of them. A retry of the experiment does not count judge runs as repetitions, and the experiment’s cost stays the agent’s cost.

The rubric

Section titled “The rubric”

A rubric is the judge’s instructions plus a declared output type. Its version is its digest: the same text and declaration give the same digest, and any change gives a new one. It is carried by the judgment request and is not part of the agent definition. Putting it there would make every rubric edit a new agent version, with its own battery, for something that does not change the agent.

The text is content, like an agent’s answer. Each judge run holds a copy under its own retention and erasure, and its opening step holds only the reference and the digest (see What the ledger holds). After retention, the judgment still states which rubric it used, and a rubric kept in the author’s own repository can be proved to be the same one.

Output types, each with its pass criterion declared beside it:

TypeThe judge answersPasses when
pass_failpass or failpass
scorean integer between a declared minimum and maximum, at most 11 valuesat or above a declared threshold
categoryone of 2 to 10 declared identifiersin a declared passing set

A category is an identifier (^[a-z][a-z0-9_]{0,31}$) rather than prose, so it can be parsed without judgment. There is no free-form JSON type and no float.

The judge never writes the value itself. The platform presents the declared values as option codes of one fixed width, A, B, C and so on in the rubric’s order, and the judge answers with a code. ok and high_risk, or 3 and 10, are then the same size in every answer. The reason for this is in Nothing left after erasure gives the value back.

A reason is off unless the rubric asks for one. The rubric declares reason: true or leaves it out, and the declaration is part of the rubric’s digest.

  • Off. The judge answers with a code alone. The parser refuses any other text, whitespace included. A code followed by a reason is judge_unparseable, not a judgment with the reason dropped.
  • On. The judge writes a code and a reason. Before the judgment starts, the console states what the reason costs, and its residual risk: the reason’s length shows in the token count, and across many judgments it may correlate with the value (see the same section).

What the ledger holds

Section titled “What the ledger holds”

The judge answers with a value and a reason. Both are content. The chain holds only where they are and what they were.

A value is not harmless because it is short. A rubric can declare fraud_suspect or high_risk, or score how a person behaved, and the value is then a classification of that person. Sealed in run_finished, it would be outside retention and erasure: the defect DP-001 records for the model answers older runs wrote inline.

  • The engine parses the judge’s answer against the rubric’s declared type. A conforming answer is written as a judgment object in the content store: the value and whether it passes. run_finished carries its reference and digest (JudgmentRef, JudgmentDigest), owned by the judge run and under its retention and erasure.
  • The reason, and the answer as the model wrote it, go where every closing answer goes: OutcomeRef and OutcomeDigest.
  • Anything else is a failed judgment, never a score: two values, a value outside the declared range or set, an answer that is not the declared shape, a ceiling reached, or a model error. The run finishes with no judgment object and a closed failure code on run_finished (judge_unparseable, judge_oversized, judge_ceiling, judge_model_error). The code says what went wrong with the judge, not what it thought of the output. There is no default value.

Nothing left after erasure gives the value back

Section titled “Nothing left after erasure gives the value back”

Erasing the bytes is not enough when what survives them can be matched against a short list. A rubric declares at most eleven values. Whatever survives an erasure and differs between those values gives the value back. Three things survive:

  • The digest. The content store derives it as SHA-256 of the bytes exactly (ledger.Content.PutFor). It stays in the chain and on the tombstone’s digest column, and its first 64 bits are part of the reference. Hashing each possible object until one matched would read high_risk back.
  • The length. An erasure sets bytes to null and keeps full_bytes and truncated (EraseOwnersTx, and every other erasure statement). Two objects that differ only in ok against high_risk differ in full_bytes.
  • The tokens. Each planning call’s cost is sealed in its step, output tokens included, and so is the run’s consumption. That is the money record and it stays. An answer that is longer for one value than another says which value in a count nobody can erase.

So every object a judge run stores about its verdict is salted and has a fixed size, and the answer it is parsed from has the same shape whatever the value:

  • Salt. When a judge run is opened, it gets 32 bytes from crypto/rand, stored as content owned by that run, under its retention and erasure. The opening holds only the salt’s reference and digest, and a hash of 256 random bits gives back nothing. The salt is never written into a step.
  • The judgment object is the salt, the option code and the pass, encoded at one fixed width and padded to one fixed size. JudgmentRef and JudgmentDigest cover all of it.
  • The judge’s answer as written is stored salt first and padded to one fixed size (8 KiB), under OutcomeRef and OutcomeDigest. That size is below the content limit, so truncated is always false. An answer longer than that is a failed judgment (judge_oversized), never truncated.
  • Nothing else holds the answer. These two are the only content a judge run writes about its verdict. A run with no tools stores no arguments, a judge publishes no artifacts, and the engine stores no proposal: PlannedPayload.ProposalRef exists, but nothing writes it.
  • The answer’s shape. The value is a fixed-width code (see The rubric), so an answer without a reason has the same length for every value, and so does the answer the platform expects.

Fixed size is chosen over clearing the length when content is erased. The length is cleared by none of the eight statements that erase content today, and these include migrations already applied. A binary from before this note would keep clearing nothing. A size the writer fixes holds against every binary that erases, including the previous one.

What remains, stated rather than hidden:

  • A reason’s length. When a rubric asks for a reason, its length shows in the output tokens, and a reason may tend to be longer for one value than another. The value cannot be read back from one judgment by matching. It may be guessed from many, by correlation. That is why a reason is off unless the rubric asks for one, and the console says what asking costs.
  • The tokenizer. Whether a provider counts A and K as the same number of tokens is the provider’s tokenizer, which the platform does not control. The platform guarantees its own side: the prompt is identical and the expected answer is the same length for every value.

The salt is not an auditable decision, and nothing branches on it. The rule against unrecorded randomness on an auditable path does not reach it: a salt that were recorded would defeat its purpose.

The copy of the judged output that a judge run holds keeps the digest the judged run already sealed, and this changes nothing about that run.

The chain keeps the provenance: the rubric digest and the judge configuration on the opening, the salt’s reference, and the salted judgment’s digest on the close. An auditor can prove which value was recorded while the content exists, and, once it is erased, only that one existed.

Only the engine writes JudgmentRef, and only on a run whose opening names a judge. A worker that does not know judges never writes it, so a run it planned can never read as a judged result.

Untrusted output

Section titled “Untrusted output”

The platform defends untrusted content today at the Gate: a label taints what derives from it, and a high-effect act on tainted arguments needs a person. A judge has no tools, so there is nothing for the Gate to stop. This needs a defense of its own, and each part is a mechanism a test can assert:

  1. Position. The platform’s judge preamble and the rubric are the system instructions. The case input and the judged output appear only in the user turn, each inside a block marked as data to be judged and never as instructions.
  2. A boundary the output cannot forge. Each block’s delimiter carries a value derived from the judge run’s id. That id is generated after the judged output was written, so the agent could not have known it. An output that contains a closing delimiter, with any other value, stays inside its block.
  3. A closed answer. Only a value of the declared type counts, and everything else is a failed judgment (above). An output that persuades the judge to write prose has produced no score.
  4. Nothing to anchor on. The judge does not see the structural verdict, the other repetitions, other runs or the agent’s own instructions.
  5. Provenance on every number. A judged result is always shown with its rubric digest and judge model, labelled as an opinion, and after held and broken.

These mechanisms do not stop an output from persuading the judge to answer exactly pass. A well-formed pass is the one answer the closed parser has to accept. No prompt makes a model immune to persuasion. The requirement in #298 is therefore narrowed, and the narrowing is the decision this note records:

  • What the platform guarantees, and tests in CI:
    • whatever an output says reaches the judge only as data;
    • it cannot alter the rubric, the boundary or the shape of the answer;
    • it cannot change held or broken.
  • What the platform measures, and does not promise: whether a given judge model, under a given rubric, can be talked into a pass. The hostile set below is also a rubric’s calibration. The installation’s owner runs it against a real model, outside CI, as a judgment like any other, and its result is that judge’s resistance, stated with its sample size.

A judged result is therefore never more than what it is labelled: one model’s opinion under one rubric, which a determined output may have bent.

Which outputs are judged

Section titled “Which outputs are judged”

  • Broken runs are not judged. A case broken in a repetition is broken, and a score for that repetition would be the second grade NT-006 §5 rules out. Not judging it also saves its cost. The report counts these as not judged: broken.

  • Runs without an answer are not judged: parked, failed, or erased. Each is counted with its cause.

  • The experiment must be complete, not only quiet. Having no open runs is not enough. An interrupted opening can leave some cases unopened, and its runs then finish and nothing is running. A retry with the experiment’s key may still open the rest, as addMissing does. So a judgment requires the experiment’s whole intention to be materialized:

    • every case its dataset version pins has a run for each repetition, or is reported as erased;
    • every one of those runs has finished.

    The check and the opening of judge runs happen inside the same exclusive corpus fence an experiment’s opening and its retries take (regressions.Exclusive). No retry can add a run between the check and the judgment. Anything short of this is a 409 that names what is missing.

    An experiment that can no longer be completed, because its pair is no longer served or its cases can no longer be read, cannot be judged. It stays a stated gap, never a judgment over part of it.

One judgment per key

Section titled “One judgment per key”

A judgment has the idempotency contract an experiment has (NT-015), for the same reason. A response lost on the way back must not, on a retry, open every judge run a second time and spend it all again.

  • The key names the judgment. Its id is derived from the agent and the Idempotency-Key, as experimentID is, never generated per request. Each judge run’s own key is the judgment id, the judged run and the repetition, so opening the same run twice is refused by the ledger.
  • The intention is recorded on every judge run’s opening: the experiment, the rubric digest (which covers whether a reason is asked for), the judge configuration, the per-run ceiling and the repetitions. It is read back from the ledger, never kept anywhere else.
  • An identical retry completes and answers. It opens only the judge runs that are missing and answers from the ledger, whatever has changed since. A field it leaves out is inherited from the recorded intention. The rubric’s text is read back from a judge run’s copy, while one is still retained.
  • A non-divergent retry is never refused because something changed underneath. This covers a provider no longer served, an erased corpus, or erased rubric content. It is answered from the ledger even when it can open nothing more, and the answer says what it could not open.
  • A divergent retry is a 409. This covers another experiment, rubric, judge, ceiling or number of repetitions.
  • Scope first. The recorded scope is authorized before anything that could answer differently. A caller with no claim gets 404 before any 409, so a retry cannot confirm a judgment it has no claim on.
  • Under the fence. Settling the intention, opening what is missing and checking that the experiment is complete happen inside the one exclusive fence.

Reading a judgment

Section titled “Reading a judgment”

A judgment shows, in this order:

  1. what it judged: the experiment, with its dataset version, agent version and configuration;
  2. the rubric digest, output type and pass criterion, and the judge’s provider, model and effort;
  3. outputs judged out of the experiment’s outputs, with each reason for one not being judged, and the repetitions. A judgment whose object has been erased is counted as erased, never as a pass, a fail or a failed judgment;
  4. the results: passing judgments out of judgments (k of n); for a score or category, the count for each value; and how many outputs were unstable, meaning their repetitions disagreed on passing;
  5. the cost.

Each case shows its own k of n, beside its structural result and never in its place. When the judge model is the model being judged, the screen says so. It is allowed, because it is often the only model available.

The judgment’s cost is its own. It is not added to the experiment’s cost, so comparing two experiments still compares what the agent cost.

Comparing

Section titled “Comparing”

Two experiments can be compared on quality only when both have a judgment with the same rubric digest and the same judge provider, model and effort. A different rubric or judge is a different question, and its numbers are not comparable. That includes a rubric that differs only in asking for a reason: an answer that has to be justified is not the same measurement as one that does not. Otherwise the comparison shows the structural side and says why there is no quality side.

When they are comparable, quality is compared over the cases that held on both sides and whose judgments are still readable on both, on top of NT-015’s rule for dataset versions. Without this, the side that broke its hard cases would be judged only on its easy ones and look better for it.

Cost and whose budget pays

Section titled “Cost and whose budget pays”

#261 asked whether judges spend the agent’s budget or a separate evaluation budget. What the code does today decides most of it:

  • A simulated run, whether a battery or an experiment run, is limited by its per-run ceiling, narrowed by its scope’s remaining headroom (Worker.scopedBudget).
  • What it spends never counts against that scope’s period ceiling. SpentSince sums real runs only.
  • What it spends never reaches the FinOps projection. finops.writeSpend skips every simulated planning call.

For phase 3, a judge pays the way an experiment does, and the person who asked for the judgment approved its stated cost:

  • the request declares a per-run ceiling for the judge, required and greater than zero, because a judge’s call is not shaped like the agent’s;
  • the console states, before it starts, the number of judge runs (outputs judged × repetitions) and their ceiling, as it does for an experiment;
  • a judgment never consumes the agent’s period ceiling, so measuring an agent cannot stop it working.

Two things stay open and are not part of phase 3:

  • Measurement is invisible in FinOps today, for batteries and experiments as well as judges. Showing it as its own line, apart from operating spend, is a FinOps change of its own. Judges make the gap bigger, so it should get an issue before they ship.
  • A separate evaluation ceiling over a period is needed when something spends with nobody asking each time. That is phase 4, and it is decided there.

Erasure

Section titled “Erasure”

A judge run holds the case input, a copy of the judged output, the rubric, the judge’s reason and the judgment object. All of these are reached by the erasure that already exists, with no new search:

  • A subject erasure follows a named run’s input digest to its corpus copies and to the simulated runs of the same agent that hold the same bytes (replaySearchSQL). It then erases each such run’s content whole. A judge run holds the case input as its own content, so it is found the way a battery or experiment run is.
  • Retention does the same through expiredReplaysSQL.
  • A simulated run’s tools answer with nothing (DryTools), so a judged output holds nothing a tool fetched. What it says about the case’s subject came from the case input, and following the input digest therefore reaches every judgment of it. Anything else an output repeats came from the agent’s instructions or its memory, which have erasure of their own.

What survives erasure is what NT-015 already keeps: the run, its steps, digests, references and provenance. The judgment object goes with the rest of the judge run’s content, value and pass included, and the salt goes with it. No classification of the person outlives the erasure, whether in the bytes or recovered from a digest or a length. The report then shows that judgment as erased and recomputes its numbers without it, saying how many it left out.

Rollout

Section titled “Rollout”

A worker on 0.101.0 that claims a judge run resolves it as an ordinary experiment run with no configuration (worker.resolve). It would plan the judged agent itself on the case input and spend its money on an answer nobody asked for. It would never write a JudgmentRef, so no false score could result. It is still a wrong run.

The experiment listing on 0.101.0 also groups every simulated run that names the experiment (experimentGroups), so it would count judge runs among the experiment’s runs.

So this ships in two releases, as experiments did:

  1. Readers and workers.
    • The simulation pool resolves a judge run as a judge, and refuses one whose opening is not simulated or names no experiment.
    • Every reader that groups an experiment’s runs leaves judge runs out.
    • Reading a judgment’s simulation id as a simulation is a 404.
    • Nothing opens a judge run yet.
  2. Writers. The API, the console and the manual. They ship only once production readyz shows release 1 on every replica, and once the FinOps issue for measurement spend exists (#317).

After the first judgment, rolling back below release 1 is not safe. Rolling back to release 1 itself is: it knows judge runs and cannot start them. As with experiments, any judgment still running should settle first.

What this is not

Section titled “What this is not”
  • A judge in the start gate, the battery or the drift sweep. Those stay structural. An opinion does not decide whether an agent may run.
  • A comparison with an expected answer. NT-015 leaves expected output out of a dataset, so a rubric judges an output on its own merits, with the case input as context.
  • Online sampling, the review queue, or an ensemble.
  • A model leaderboard (NT-006 §8). A judgment belongs to one agent’s experiment.

Tests that must exist

Section titled “Tests that must exist”
  • Gate: a judge run, from the writer’s own opening, neither lets a version start nor stops it, does not count as a battery, and does not let an agent leave Draft. The readers are the ones already deployed, on Postgres and on the fake.
  • Experiment intact: after a judgment, the experiment’s report, its listing counts, its cost and the answer to a retry with its key are the same as before. Sabotage: remove the exclusion from each experiment reader in turn, and a test must fail each time.
  • Old worker: a judge run claimed by a pool without judge resolution never writes a JudgmentRef, and the report counts it as failed.
  • Complete, not quiet: an experiment whose opening was interrupted, whose runs have all finished and which a retry could still extend, is a 409 to a judgment. So is one that can no longer be completed. A retry of the experiment racing a judgment cannot add a run the judgment then misses. Sabotage: check only for open runs, and the test must fail.
  • Idempotency: a retry with the same key after a lost response opens no second judge run for any judged run and repetition, completes one interrupted halfway, and answers from the ledger. A retry that leaves fields out inherits them. One that changes the rubric, the judge, the ceiling, the repetitions or the experiment is a 409. Once judge runs exist, a retry whose pair is no longer served is still answered. A caller outside the recorded scope gets 404 before any 409. Sabotage: generate the id per request, and the duplicate test must fail.
  • No surviving metadata tells the outputs apart:
    • With a fake model, run one judge run per declared value, without a reason, then erase them.
    • A judge run’s content rows are exactly the salt, the input, the copy of the output, the rubric, the answer and the judgment object. A seventh row fails the test.
    • Compare everything that survives: each content row’s digest, full_bytes, truncated, seq and owner kind, and each step’s payload other than ids and digests of salted objects.
    • It must be identical across values. No enumeration of the declared outputs, as a judgment object or as a bare answer, may reproduce any digest or the 64 bits in any reference.
    • Sabotage, one at a time, and the test must find high_risk each time:
      • store the objects unsalted;
      • drop the padding;
      • let the judge write the value instead of its code.
  • Reason off: with the reason off, an answer of a valid code followed by any text, even a space or a newline, is judge_unparseable. Sabotage: trim the answer before parsing, or accept a valid prefix, and the test must fail.
  • Reason declared: changing only reason changes the rubric’s digest. A retry under the same key that changes it is a 409.
  • Oversized: an answer one byte over the fixed size is judge_oversized, and never a stored, truncated object.
  • Nothing personal in the chain: a test reads the run_started and run_finished payloads of a judge run and fails on any field that is not an id, reference, digest, configuration or closed failure code. The value, the pass and the salt have to be absent. Use the value the bug would accept: a category such as high_risk.
  • Fence: a judge on a non-simulated run, or on one with no experiment, is refused by the opener and again by the pool.
  • No tools: a judge run’s pack is empty, whatever the judged agent declares.
  • Hostile, structural isolation only: this test does not claim the judge resists persuasion. That is measured, as described in Untrusted output. With a fake model that records what it was sent, outputs that impersonate the rubric, forge a closing delimiter, or announce their own score appear only inside their data block, never in the system instructions. Every answer that is not a single value of the declared type is a failed judgment, and never a pass. Use the values a permissive parser would accept: a value with trailing prose, two values, an out-of-range integer, an undeclared category.
  • Structure first: a run broken in a repetition is not sent to the judge, and no judged result changes held or broken.
  • Comparison: different rubric digests, or different judges, give no quality side. The same rubric with and without a reason has two digests, and gives none either. Comparable judgments compare only cases held on both sides.
  • Erasure: a subject erasure of the run a case came from erases every judge run of that case’s replays: the copy of the output, the reason and the judgment object, value included. The report then counts those judgments as erased and nothing else changes. Retention does the same.
  • Ceiling: a judgment request without a positive per-run ceiling is refused, and a judge run that reaches its ceiling is a failed judgment.
  • Scope: a judgment is read, listed and requested only in the scope the experiment was recorded in, and every door answers 404 before any other answer.
  • Journey: from the API, through a settled experiment and real judge runs, to the report, on real Postgres.

Decided

Section titled “Decided”

Decided by the reviewer on 2026-11-10:

  1. Budget, for phase 3:

    • the judge pays as an experiment does;
    • a per-run ceiling is required;
    • the agent’s period ceiling is never touched;
    • a separate period ceiling waits for phase 4.

    This is conditional: the issue for a FinOps line for measurement spend must exist before the writers (release 2) ship. It is #317.

  2. Broken runs are not judged.

  3. The rubric lives in the request, addressed by its digest, not in the agent definition.

  4. The judge model may be the judged model, with the screen saying so.

  5. A reason is off by default and asked for only when the rubric declares it, because a reason’s length survives in the token count (see Nothing left after erasure gives the value back). The declaration:

    • is part of the rubric’s digest;
    • is part of the idempotent intention;
    • makes a judgment with a reason not comparable with one without;
    • when off, makes the parser refuse any text beyond the code;
    • when on, means the cost and the residual risk of correlation through the token count are stated before the judgment starts.

  6. The untrusted-output requirement is narrowed. The platform guarantees structural isolation and measures resistance to persuasion; it does not promise it (see Untrusted output).
